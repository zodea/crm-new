## 失败复现与修复

1. 原批复保存把未填写压成零；旧表非空默认零和详情零回退申请额分别由数据库/保存/详情公共测试复现。修复后 null 与明确零独立往返，旧零只标未知。
2. 临时输入负数曾使严格金额读取器抛出渲染异常。组件反例先失败，现输入态可编辑并提示修正，保存域仍拒绝负数及非有限数。
3. 同 ID 缓存详情在编辑保存后未重读，原测试仍显示未填写/100，现读取明确零/0。独立复核又复现重读挂起或失败仍残留旧100与登记按钮；现先撤旧事实，失败可见，重试可读取0，停用期间的迟到响应失效。
4. 浏览器准备阶段的等待/定位错误不计为产品缺陷：新表单尚未读取数据库便取快照；把保存时禁用当作保存完成；label 误匹配同名金额 group；管理按钮还包含编号。已改用真实初始化入口、完成状态与控件角色。

## 独立发现的页签恢复断点

保存后回列表整页重载，再从真实表格名称行打开已经存在的未恢复付款详情，会被旧恢复状态阻断。这在限定 KitTable 的真实点击下仍复现，不能仅归因于同名定位。截图为 [tab-restore-reopen-blocked.png](./tab-restore-reopen-blocked.png)，已在 [#435 留证](https://github.com/zodea/crm-new/issues/435#issuecomment-5623599959)。

该已定技术缺口由 #435 下一独立工作单元修复，不转为业务 grill。#439 最终金额持久化验收先通过可见“关闭未恢复详情页签→从列表重新打开”核对，未放开未接入详情的自动恢复，也未把该恢复断点标为通过。

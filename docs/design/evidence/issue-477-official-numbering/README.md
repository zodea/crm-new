# #477 工资正式编号与单份出具验收

对应 [Issue #477](https://github.com/zodea/crm-new/issues/477)。实际范围是已有完整冻结证据的 A/C1/C2 原工资、项目起点登记、首次正式出具、同号输出与受控迁入。纸号边界见 [Issue 澄清](https://github.com/zodea/crm-new/issues/477#issuecomment-5770341996)；长期规则只看[工资页面](../../../rewrite/pages/subcontract-payroll.md)、[数据模型](../../../rewrite/DATABASE.md)、[命令](../../../rewrite/COMMANDS.md)和[读取合同](../../../rewrite/READ-MODELS.md)。

## 服务与恢复实测

2026-09-22，真实 SQLite 内存事务、中央公开工资命令与公开迁移准备/确认流程驱动的定向用例通过：5 个测试文件、21 项测试，13.32 秒。没有用“完整已发”健康快照种子替代生成工资过程。

| 场景 | 实际结果 |
| --- | --- |
| C2 冻结实发 525，登记下一号 128，首次正式出具 | 读回字符串 `128`、序列 129、原实发仍为 525；重复出具和下载不推进序列 |
| 同一原单双窗提交；同项目 C1/C2 不同原单竞争 | 一次成功、陈旧提交明确拒绝；原单重新读取沿原号，另一原单重试取得下一号 |
| 回执插入触发失败、等待过程中撤销权限 | 整个事务回滚，未留下正式记录、已占号或半份审计；恢复权限后原键可提交 |
| 提交成功后 HTTP 响应丢失 | 原键核对返回原 `128`，数据库只保存一份正式出具；HTTP 金额为十进制文本，浏览器 DTO 正确解码 |
| 错操作者、跨项目、同键异文、只读用户、未知字段 | 按权限或严格协议拒绝；只读用户可读已证明的原号输出，但不能新增出具 |
| 起点/序列、原件摘要、项目或回执正文损坏，回执缺失 | 读取不可用且不能猜修、重新编号；未发、B、缺来源和未知原单不能占号 |
| 起点物理行及回执结果同时更改登记人，原命令仍为原操作者 | 新增失败复现先失败；补充初始化结果与可信命令身份交叉校验后拒绝读取，没有生成正式号 |
| 带编号完整图首次及重复受控迁入 | 外层 V5 保留编号文本、原件摘要、原 JSON 和显式身份映射；旧 V1–V4 图不补编号字段；重复确认不覆盖日常事实 |
| 迁入后重复出具，再尝试撤销所属来源 | 保持原号、下一号不变；新增日常回执构成恢复引用，危险准备整批拒绝且原状态不变 |
| 不相关项目仅登记自己的起点 | 不错误阻挡撤销另一个工资项目的来源 |
| 迁入 A 实发 550，登记并出具 501，再连续两次完整迁入 | 原号 `501`、原摘要、下一号 502 和 550 原实发保持；HTTP 冻结文档往返一致；再次篡改物理摘要后冷读取拒绝 |
| 已证明祖先编号回执的恢复引用 | 按完整原图证明隔离原 JSON 与本代 SQL 身份；仍收集本代项目及原工资引用，不凭 ID 外观跳过校验 |

复现文件：`central-official-numbering.test.ts`、`central-numbering-integrity.test.ts`、`numbering-controlled-migration.test.ts`、`numbering-migration-chain.test.ts`、`numbering-http.test.ts`，均位于 `tests/payroll/`。多代原图回归扩展后已再次单独通过。

## 验证边界

当前类型检查和定向代码规范检查通过；最终集成全量测试、构建及独立审查在本票最终提交时登记。本证据不代表生产磁盘保存、进程重启耐久或灾备演练已完成；这些由 ADR 0021 的生产实施票逐项验收。完整工作簿与按月归档组合由 [#479](https://github.com/zodea/crm-new/issues/479) 承接。

旧纸号先由经办人核对后登记下一号。旧八表没有编号字段；不凭口述向电子工资贴历史号，不自动扫描纸张重复、不补缺号，也不伪造旧出具回执。

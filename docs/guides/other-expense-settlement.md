## 一、采用真实原费用

1. 在正式浏览器工作区打开“其他支出结算”，点击“新建结算”。整页表单默认采用“无合同原费用”。
2. 选择真实项目，或保持公司归属。点击“重新核对原费用来源”，选中该归属下已确认的原费用行；核对原费行编号、服务交易方及垫付人。
3. 填写本次采用金额、结算名称及日期。采用金额未填写时只能保存草稿，明确填写零仍保留为零。实际垫付收款人继承原费用，服务交易方单独显示。
4. 登记原件后，明确选择“保存”或“保存并提交”。待确认结算在编辑页选择“确认结算”，随后进入只读详情。
5. 在付款申请中明确采用该已确认结算，并核对同归属、同一真实收款人。付款登记沿原申请记录实际支付及凭证；结算确认本身不会出现银行付款。

列表的“已确认”筛选同时包含当前确认记录与保留原状态的历史确认记录，具体口径见[支出结算事实](../rewrite/DATABASE.md#ax05-其他支出结算中央事实)。

历史申请编辑页出现“历史付款业务核验”时，先核对该申请采用的原费用、已确认结算和已保存原件，填写“核实累计应付金额”“核实累计可付金额”及“业务核验依据”，勾选实际依据原件，再点击“保存业务核验”。核对页面显示的核验人、时间及结论后，继续沿原申请登记并确认实际回单；提交未知仍使用原编号核对。适用范围、原批复与既有现金的保全以及当前来源复验统一见 [PAY-08](../rewrite/DATABASE.md#entity-payment-record)，原编号与读回操作见 [COMMANDS](../rewrite/COMMANDS.md#success-receipt-and-readback)。

字段、来源及金额的唯一规则见 [DATABASE 的支出结算事实](../rewrite/DATABASE.md#ax05-其他支出结算中央事实)和[费用报销与明细](../rewrite/DATABASE.md#费用报销与明细)，票款写入与原命令约束见 [COMMANDS](../rewrite/COMMANDS.md#ax05-其他支出结算命令)。本页说明操作，不维护另一套计算规则。

历史清偿承接方案已于 2026-10-05 确认，规则直接见 [DATABASE](../rewrite/DATABASE.md#historical-expense-clearance)。原清偿单缺失时，先打开原费用整页，上传真实银行流水、签收或原账等替代依据，点击“保存新增替代原件”；在“旧清偿替代核验”选择原费用行，逐项选择真实原记录或明确补证来源，填写处理金额、匹配依据和说明，勾选已保存替代证据后“保存旧清偿替代核验”。核定结果分别显示新可采用额度与旧义务，不能把处理份额理解为已付现金；完全缺证时保持未知。原纸缺失、替代核定、合并采用、申请及真实实付已通过正式整页、冷读和五档界面验收；精确外部电子原单缺失声明的分层验证边界见上述权威规则。工人工资继续使用工资实际收付流程。

回到其他支出结算，选择同一原费用，在“旧份额关联与待实付”明确勾选实际已核旧份额及本次金额；页面分别显示“本次新增采用”“承接已核旧份额”和“总采用”，再同次保存或提交。已确认旧结算从详情进入“核对旧份额关联”，只能选择该结算的真实采用行，填写实际旧份额后“保存旧份额关联”，原结算正文及现金不变。旧未付继续沿原结算关联付款申请，不另建一笔原费用；输入或来源未核实不能靠普通保存绕过。原编号、已保存读失败及后来输入继续沿下节恢复。

## 二、合同与金额核对

已有其他支出合同的结算继续从真实合同详情的“支出结算”页签进入，或在整页表单明确选择合同分支。该合同来源仍沿实际 Native/开发验证 owner；正式工作区未注册对应合同来源时，候选不可用，不能拿开发样本代替正式合同。

详情按实际来源显示结算金额、奖罚抵扣、净额、申请及支付，并可沿稳定编号查看申请与支付源单。没有可靠归属或来源未接通时，金额显示“未记录”；不能把它理解为无需支付。查询及完整来源范围见 [READ-MODELS](../rewrite/READ-MODELS.md)。原合同作废不会删除已确认结算、抵扣或现金历史。旧申请或采用关系已经删除、撤回而仍有真实确认支付时，详情继续保留该现金；申请余款无法可靠证明时显示缺口，不能据此新增申请。

名称主链接进入只读详情，“编辑结算”打开独立整页。确认后不允许改挂来源、换收款人或改写金额。详情的版本选择保留当时采用的原费用、收款姓名、原件及审计；后来的资料不能覆盖已冻结版本。真实正文已核验的原件可以预览、下载；缺正文的历史登记会明确显示缺口。

详情上方标注“当前”的金额仍是当前口径；所选冻结版本不可用时请重新读取，系统不会以当前附件或审计替代历史证据。

## 三、提交未知、读回失败与冲突

- 显示“提交结果未知”时，先点“核对原提交”，沿原编号查明结果。核对完成前写按钮保持关闭。
- 已知保存成功但读取失败时，核对入口只重试读取。输入、原件和原编号仍保留。
- 请求期间增加的内容按[同目标后读规则](../rewrite/COMMANDS.md#success-receipt-and-readback)保留在当前页，核对后继续保存同一记录；若原动作已确认结算为冻结状态，本页提示冻结并关闭继续写入。
- 版本冲突时，先核对最新资料。明确选择“采用最新版本”会替换当前输入及待上传原件；否则保留自己的内容。
- 身份、权限或来源切换后，恢复原会话再核对原编号。旧会话的迟到响应不成为当前成功结果。

未保存页面离开或关闭前会提示。返回来源继续保留筛选、页码、页签、滚动位置及行焦点。

## 四、完整历史迁入

在 Native 的“设置 → 数据迁移”导出当前数据库一致快照，保留原库与该快照。在正式浏览器的结算列表点击“原结算历史迁入”，选择完整 SQLite 文件。

服务读取实际完整字节及 SHA-256，展示原结算图与主档关系。逐条选择真实目标项目、分供方或工人，填写身份核对依据，确认后迁入。目标版本变化或遗漏关系时，本次不写入；保留当前选择并重新核对。迁入结果未知时使用“核对原迁入”，已知保存但读取失败只重试读取。

原稳定编号、原头、原采用行、原件、旧审计、原命令及原身份封存在同一迁入证据中；当前关系按已确认映射投影。旧回执不授权新的中央提交。当前可付款净额仍须由真实原费用及当前票款来源核验，未接通的旧奖罚和支付保持未知。

迁入后，如果同一原费用的已确认采用合计超过真实原费用上限，详情保留原结算金额、原历史及真实已付现金，并明确显示当前新申请资格不可用。核对前不能沿这些结算再次申请，迁入不会自动改写或重新分摊历史。

一般结算原件仍须沿完整原图核真实字节，历史元数据缺件与当前正文损坏分别保留原因。原清偿单缺失的精确例外从财务原库迁入预检逐件声明，原文件名、路径、未知大小及缺失事实保留；它不豁免结算、原费用、银行回单或其他 owner 的正文损坏，具体适用范围只见 [DATABASE](../rewrite/DATABASE.md#historical-expense-clearance)。

## 五、当前边界

正式服务复用当前业务存储、同事务持久化与原编号回执，冷重启后仍可核对。Native 当前没有可信的中央结算身份，不能借 HTTP 会话新写；本地历史读取及一致快照导出继续保留。辅助合同、旧奖罚来源或完整外部审批尚未正式接通的部分，页面明确显示不可用，不生成替代事实。

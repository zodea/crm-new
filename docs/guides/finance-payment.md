## 一、当前可用能力

已认证中央工作区的费用报销、往来款、付款申请、支付记录和开票申请使用实际持久来源，保留稳定身份、版本、原回执、历史及原件。旧桌面资料须从“设置 → 数据迁移”逐项核验后采用；操作见[本地数据迁移指南](./local-data-migration.md)。演示数据按授权只读；运行与数据归属直接见 [ARCHITECTURE](../rewrite/ARCHITECTURE.md#read-write-boundaries)。

| 能力 | 当前进度 |
| --- | --- |
| 从付款申请列表、付款管理进入只读详情 | 已实现 |
| 查看申请金额、已批金额、已付金额、未付金额 | 已实现 |
| 区分未填写、明确批复零元和历史批复待核验 | 已实现；详情、付款管理和分供方相关摘要保持一致 |
| 查看合同、结算、发票和支付源单 | 实际来源可读时使用当前数据；旧冻结依据与未知当前净额分别显示。来源缺失或无权限时保留原因及原稳定 ID |
| 查看跨项目付款摘要 | 只按明确工人或分供方身份计算；缺身份或失去支付读取权限时保持未知 |
| 智能业务洞察：审批状态、结算勾稽、发票勾稽、付款上限 | 已实现 |
| 从详情进入编辑付款申请 | 已实现 |
| 从详情或付款管理登记支付并回填剩余金额 | 已实现 |
| 审批与通知展示 | 只使用已有真实状态或事件；完整审批引擎不在本轮范围，通知联动仍需专项复核 |

付款管理与付款申请详情共用当前正式清单及真实分摊；读取期间版本、身份或权限变化时撤下旧正式事实，重新读取后再登记支付。测试工作台只读。金额来源未知时保持未知，可靠读到空集或真实零才显示零；公共规则直接见 [READ-MODELS](../rewrite/READ-MODELS.md)。

## 二、查看付款申请详情

1. 进入“资金管理 → 付款申请”或“资金管理 → 付款管理”。
2. 点击付款申请名称，进入只读详情页。列表中的编辑动作仍进入付款申请整页表单，不会把查看和编辑混在同一页面。
3. 在详情页先核对顶部摘要，再查看基础信息、合同状态、结算关联、发票关联和支付记录。
4. 只有稳定 ID、数据来源和目标权限均有效的蓝色源单链接才能进入合同、发票或支付记录；缺关系或目标尚未接入时显示不可用原因，不根据名称或金额猜测关联，也不跳入另一数据来源。

批复金额显示“—”时，应同时查看旁边的说明。“未填写”表示没有录入批复金额；“历史批复待核验”表示旧记录不足以证明当时的批复含义，需要核对原始凭据。后者的待支付余额和完整合计也会保留未知，不能理解成没有欠款。已确认的银行支付仍显示真实金额。

## 三、阅读智能业务洞察

右侧“智能业务洞察”根据当前数据库中的付款申请、合同、结算、发票和支付记录实时派生，不是静态提示图。

- **审批状态**：展示已有申请状态及相应提示；状态提示不代表系统提供了审批流程，不能据此推断新的审批入口或自动审批规则。
- **结算勾稽**：核对当前类型所需的真实结算分摊。无合同费用先核验原费用并在原结算入口采用，再关联付款申请；详细归属与额度直接见 [DATABASE](../rewrite/DATABASE.md#contract-freight-treatment)。
- **发票勾稽**：按实际回票类型查看关联状态；“待回票”指标只在适用的申请详情中出现。金额或类型尚未核实时显示原因，不能理解为零元；关联要求和计算直接见 [DATABASE 的付款申请规则](../rewrite/DATABASE.md#entity-payment-application)。
- **付款上限**：检查已登记的确认支付是否超过申请/批复金额，并显示当前未付余额。未付余额本身是待办信息，不等于异常。
- **跨项目/分供方付款**：展示同一分供方在其他项目上的可追溯付款摘要，帮助复核集中付款，不替代项目级审批。

提示级别分为正常、信息、注意和异常。注意与异常会计入顶部待处理数量；每条提示都应回到源单核对后再处理。

## 四、登记支付

1. 在付款申请详情点击“登记支付”，或在“付款管理”对应行点击登记支付。
2. 系统进入“新建支付记录”整页表单，并从真实付款申请带入项目或公司归属、分供方或工人收款身份及当前可登记金额。工人工资从工资实际收付流程处理；这里的工人收款承接原垫款清偿。
   有合同且需要发票时，先在付款申请中关联并核对该合同的发票，再确认实际支付；预付款和“先款后票”也适用。合同或发票来源缺失、无权限或不一致时按提示核对，支付草稿仍可保留。此规则的代码仍在隔离验收，运行中的局域网服务尚未更新；具体规则见[付款页面规格](../rewrite/pages/finance-payment.md#合同与发票核对)。
3. 核对支付日期、支付方式、收款账户和本次支付金额；金额以实际银行支付为准，不要直接接受回填值而跳过核对。
4. 完成原支付记录的人工核对后，再回到付款申请详情确认已付金额和未付金额已按真实支付记录更新。保存草稿或待核对状态不表示已经支付。

更正已被实际支付采用的申请时，先从原支付记录核对银行事实及撤回确认，再处理申请；直接删除会提示冻结保护。若旧历史已删除申请但仍有确认现金，保留原支付、原件和历史，先核验原分摊与余款资格，再继续申请。额度与冻结依据直接见 [DATABASE](../rewrite/DATABASE.md#contract-freight-treatment)。

本次已保存但读取核对失败时，表单会保留原输入、附件和原回执并暂停再次写入。点击“只重试读取”核对同一记录；后来增加的字段或附件仍保留为未提交输入。结果未知时点击原提交核对入口，刷新后继续核对同一编号；核对为未应用后才重新准备提交。登录、权限或来源变化会撤下旧读取结果并保留输入。公共恢复规则直接见 [COMMANDS](../rewrite/COMMANDS.md#idempotency-and-recovery)。

如果已知可付金额已经全部支付，详情页不会继续提供可用的登记支付动作；如果只支付了一部分，下一次登记支付只回填剩余金额。明确批复为零元时，不会自动改按申请金额继续支付。

历史批复待核验的记录从“编辑申请”进入原整页的“历史付款业务核验”。先保存申请编辑和依据原件，再填写两项累计金额及业务依据，选取已保存原件并点击“保存业务核验”；可靠读回后查看冻结核验及当前来源状态，再从原申请登记真实支付。来源不可用时保留回单草稿并按页面原因核对。登记回填不能替代业务核验；适用范围及原批复、余额和既有现金的保全直接见 [DATABASE](../rewrite/DATABASE.md#entity-payment-record)，原提交恢复见 [COMMANDS](../rewrite/COMMANDS.md#f3-finance-payment-verification)。

## 五、编辑付款申请

1. 在详情页点击“编辑申请”。
2. 编辑页仍使用付款申请整页表单；保存、提交等写入动作只在表单中进行。
3. 保存后返回详情重新核对合同、结算、发票和支付勾稽结果。若金额或关联源单发生变化，智能业务洞察会重新计算。

在隔离验收中的新版本，先选项目和实际收款分供方，再选择真实合同；公司付款可选已有公司支出合同，不需要虚构项目。旧申请若提示合同领域待核实，须重新选择对应合同；合同变更后须重新核对版本。有合同且需要发票时可先保存、提交申请，在实际支付确认前选择同一合同的发票；先票后款还须在确认前核对发票关联金额等于申请金额。项目付款选择同一项目的票，公司付款选择公司开销票；原关联若不符合归属，须核对后才能进行新的支付确认。结算来源缺少合同身份或读取权限时不能采用，不凭同号判断。具体业务规则见[付款申请页面规格](../rewrite/pages/finance-payment.md)。本段描述代码中的隔离验收范围，局域网运行服务尚未更新。

如果提示合同版本变化，点击“重新读取合同”，然后重新选择并核对同一合同；申请金额和已填分摊保留，并在保存时重新核验。改选其他合同时，原合同的关联分摊会清除，须重新选择。

切回已经打开的付款详情时，页面会重新读取保存结果。整页重载后若出现未恢复提示，可直接从付款申请列表重新打开，无需先关闭旧页签；付款详情自动恢复尚未接入，记录不会因此删除。重新打开与重试恢复的区别见[页签与页面恢复指南](./tabs-and-recovery.md#四恢复失败如何处理)。

“本期批复金额”留空表示未填写；填写 `0` 表示明确批复零元。已填金额可以清空，保存并刷新后仍为空。历史待核验记录按 [DATABASE 的已确认核验流程](../rewrite/DATABASE.md#entity-payment-record)核对真实业务依据；有依据的人工更正与新支付核验分别留痕，不通过重填批复对平。仅修改审批备注、保存其他字段或点击“放弃修改”，都不会确认历史批复的含义。输入负数或无效金额会被拒绝，保存失败不会留下金额与来源的部分修改。

关联结算只可选择已确认的记录，草稿、待确认或仅审批通过的记录不会进入候选，也不计入合同往期结算和项目动态成本。保存时系统会再次检查：若源结算尚未确认，需先回到源单核对，不会留下半份付款申请或分摊记录。现有来源尚未提供确认入口时，应等待对应结算流程补齐，不能以待确认状态代替确认。

桌面财务旧库在“设置 → 数据迁移 → 财务原库迁入”选择完整一致快照并逐条核对身份。预检明确允许的旧清偿外部原单确已丢失时，可勾选“声明旧清偿原单缺失”并填写真实缺失说明；原名称、路径、大小未知与缺失状态继续保留，不用任意新文件补大小。其他费用、银行回单或已保存正文的损坏继续按原件核验要求处理，不能一并勾作缺件。迁入仅保全事实，之后仍须在原费用整页核实替代证据与份额；实际接线及当前验证边界见 [DATABASE](../rewrite/DATABASE.md#historical-expense-clearance)。

## 六、使用边界与后续能力

付款管理的“工资实际收付”是独立只读分区，按工资项目查看并进入原工资收付记录。它不改变付款申请待付、银行支付或往来指标；补退需从工资原更正进入专门整页，见[工资更正与实际收付](./payroll-adjustments.md)（P4 集成验证中）。

- 费用表单先从所属资料库的工人或分供方清单选择报销／垫付身份，再选择实际服务分供方并添加送货单、收据等原件。个人临时金的实际往来方先按分供方建档；工资实际收付从上方工资流程进入。身份与费用归属直接见 [DATABASE](../rewrite/DATABASE.md#contract-freight-treatment)，各入口只能使用同来源候选。
- 已记录垫款的清偿从“清偿原费用”选择原明细；历史来源身份尚待核实时只能保留草稿。无合同费用在原其他支出结算入口采用核实后的原明细，再关联申请和实际支付。2026-10-05 已确认的[历史清偿方案](../rewrite/DATABASE.md#historical-expense-clearance)允许原清偿单缺失时用真实替代证据交叉核实：在原费用整页先“保存新增替代原件”，再填写“旧清偿替代核验”并选择已保存依据；返回原其他支出结算明确关联旧份额及新采用部分，旧未付继续沿原结算关联申请。该限定原费用流程已通过正式整页、冷读和五档界面验收；不能把费用清偿或银行总额直接当成已核实采用份额。字段见[费用报销页面规格](../rewrite/pages/finance-reimbursement.md)。
- 详情展示当前可验证来源的派生结果，旧冻结依据明确标出；未提供事实的审批人、时间和外域金额保持未知。
- “已付金额”只统计真实支付记录中已确认的支付分配；草稿或待复核支付不会被当作正式已付。
- 付款申请详情目前没有直接执行审批、批复或发票登记的入口；本指南不声称这些动作可在其他页面完成，只有现行模块规格和真实入口共同支持的操作才可使用。
- 完整审批引擎和跨项目审批工作台不在本轮范围。通知事件、已读与安全导航、服务端洞察可用性仍按公共能力任务复核，未通过前不得把本地检查卡片当作该链已完成。
- 当前正式财务已接入统一持久化和备份核验机制；部署位置、备份任务配置与恢复验收按[本地备份与恢复指南](./local-backup-and-restore.md)执行。历史仅元数据的缺件不会变为零字节原件。

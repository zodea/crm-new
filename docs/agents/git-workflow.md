# Git 提交、推送与合并收尾

本地钩子由 Husky 管理，`pnpm install` 的 `prepare` 会启用它们。检查入口在 [`.husky/`](../../.husky/)，暂存路径与推送判定逻辑在 [`scripts/git-hooks.mjs`](../../scripts/git-hooks.mjs)，提交说明交给 commitlint。采用 #493 的分工：频繁提交只做快速检查，推送代码前做完整验证。GitHub Actions 仍按 [`ci-usage.md`](./ci-usage.md) 手动确认后调用。

## 提交前：pre-commit

按顺序执行，任何一步失败都停止提交：

1. `git diff --cached --check`：检查暂存改动中的新增冲突标记和空白错误，不扫描未暂存的工作内容。
2. `node scripts/git-hooks.mjs staged`：读取暂存的新增、修改、复制、重命名与类型变化路径，阻止临时目录、嵌套工作树、构建产物和缓存误入版本库。删除历史误入产物的操作允许通过。
3. `pnpm exec lint-staged`：按 [`.lintstagedrc`](../../.lintstagedrc) 检查暂存代码的 ESLint 规则。没有 `--fix`，不自动格式化源码；报错后修改具体文件、重新暂存再提交。lint-staged 自身仍可能临时备份并还原部分暂存文件，这不等于完全不操作 Git 暂存区。

提交钩子不执行全量类型检查或测试。开发过程中按任务风险做验证的责任不变。

## 提交说明：commit-msg

`pnpm exec commitlint --edit "$1"` 让 `@commitlint/cli` 直接读取 Git 传入的提交说明文件。配置在 [`commitlint.config.mjs`](../../commitlint.config.mjs)，继承官方 `@commitlint/config-conventional`；不再维护自写正则、解析器或合并消息白名单。两个包均为开发依赖，Node 版本要求见其包声明；当前开发环境 Node 24 满足要求。

- 普通说明遵循 Conventional Commits；scope 可省略，支持 `!` 破坏性变更标记，说明不能为空。
- 例：`chore(repo): 补齐提交钩子`、`fix: 修正合计`、`feat(api)!: 调整接口`。
- 类型、非空标题、标题/正文/页脚长度及空白等检查采用官方规则；标题最多 100 字符，正文和页脚单行通常最多 100 字符（官方正文规则允许 URL 长行）。正文、页脚缺少前导空行按官方预设提示警告，不升级为提交阻断。
- Git 标准合并、回退和 fixup/squash 等辅助消息使用 commitlint 默认忽略规则；完全空的提交说明由 Git 自身拒绝。
- 仅关闭 `subject-case`，让中文说明能自然混用 Nuxt、API 等专有名词；提交类型仍须小写，scope 可省略。
- 中文说明的准确性由作者与审阅确认，钩子不以是否出现汉字判断业务含义。

Husky 负责触发时机，lint-staged/ESLint 负责暂存代码，commitlint 负责提交说明；临时文件拦截、推送内容与当前工作目录一致性、合并后分支清理属于仓库策略，不由 commitlint 替代。规则参考：[commitlint 配置](https://commitlint.js.org/reference/configuration.html)与[官方规则](https://commitlint.js.org/reference/rules.html)。

## 推送前：pre-push

Git 向钩子传入远端名称，并在标准输入中逐行提供本地/远端引用和提交编号。脚本依次做以下判定：

1. **解析范围。** 输入损坏或读取比较范围失败时停止推送；删除引用直接跳过代码验证。
2. **确定基准。** 已有远端引用与其旧版本比较；新引用与该远端 `main` 的共同祖先比较。新引用找不到基准时完整验证，不默认为文档。
3. **判定是否跳过。** 仅仓库根目录 Markdown，以及 `docs/` 内明确的文档/证据扩展名允许跳过；代码、JSON、CSS、配置、脚本、钩子和未知文件都执行完整验证。重命名按删除旧路径和新增路径计算，避免将代码改名为文档而绕过检查。
4. **核对版本。** 所有需要验证的引用必须指向当前 `HEAD`。一次推送多个不同代码版本时停止，并提示到各自工作目录分别推送；多个引用指向同一版本只验证一次。
5. **核对工作目录。** 已跟踪的源码/配置必须与 `HEAD` 一致，也不能存在未被忽略的新源码/配置。无关文档及已被 Git 忽略的临时目录不阻止推送。脚本不自动暂存、stash 或回退用户改动。
6. **完整验证。** 运行 `pnpm typecheck && npm test`；前者失败时不继续测试，任一检查失败都阻止推送。`npm test` 按现有脚本运行单元与组件测试，不含 E2E、视觉回归或 Rust 测试。
7. **再次核对。** 检查期间 `HEAD` 或源码/配置发生变化时仍阻止推送，要求重新验证。

无标准输入元数据而直接运行推送脚本时，视为当前 `HEAD` 的完整本地验证。钩子是本地防误操作措施，可被 Git 的跳过选项关闭，不能替代必要的评审或 CI。被忽略的依赖、环境文件不属于提交快照一致性检查；依赖安装和环境准备仍由开发者负责。

## AI 临时文件与缓存

忽略路径的权威配置在 [`.gitignore`](../../.gitignore)。根目录的 `.tmp/`、`tmp/`、`temp/`、`.codex-tmp/`、`.worktrees/` 用于本地过程文件或工作树；AI 本地会话、工具缓存也单独忽略。共享规则、技能、正式文档与验收证据保持可追踪，不整目录忽略 `.codex/` 或 `.agents/`。

`.gitignore` 不会取消已有文件的跟踪，也不会删除本地文件；提交路径检查补充拦截被强制暂存的明确临时产物。完成任务仍要按临时文件清理规则回收本次创建的过程文件，不能把“已忽略”当作“已清理”。正式产物先移到任务指定的交付位置。

## 合并后的工作分支清理

每次获授权的合并完成后，把对应工作分支的清理作为同一任务的收尾；已有历史分支的批量清理由单独任务处理。直接在 `main` 开发的任务无需创建或删除工作分支。

1. **核实合并结果。** 查看 PR 的 `MERGED` 状态、目标分支和实际合并提交；刷新远端引用并确认合并结果已在目标分支。仅关闭 PR、关闭 Issue 或看到远端分支消失，不是已合并证明。
2. **列出精确对象。** 记录本地分支、远端分支、各自当前 SHA 和关联工作树。保留 `main`、默认分支、长期共享分支及仍承接其他任务的分支；不按前缀或更新时间批量删除。
3. **确认没有后续工作。** 普通合并用 `git merge-base --is-ancestor <候选SHA> <目标分支>` 验证每个候选端点。不能只依赖 `git branch -d` 的上游判断。PR 合并后新增的未合并提交、依赖该分支的开放任务或其他会话继续使用的分支应保留并报告。Squash/rebase 改写过提交身份时，核对 PR 原始 head、合并结果和实际补丁等价性；证明不足时保留，不因 PR 显示已合并直接强删。
4. **先处理工作树。** 用 `git worktree list` 定位占用；检查该目录的已跟踪改动、未跟踪文件和被忽略文件，确认没有活动会话、进程或独有资料。已归档的正式证据先保全；数据库、密钥、浏览器配置、用户文档及归属不明文件不得随工作树删除。回收遵守当前项目的临时目录、路径核验与可恢复清理规则；条件不满足时保留工作树和本地分支，报告待处理原因，禁止 `worktree remove --force`。
5. **删除精确分支。** 切离待删除分支后，用 `git branch -d <精确分支名>` 删除已证实合并的本地分支；拒绝删除时查明原因，不自动升级为 `-D`。删除远端前再次读取它的当前 SHA，并以预期 SHA 的 lease 删除精确引用，防止覆盖合并后别人新推的提交；若 SHA 已变化，重新核验。远端已不存在则记录为已清理，无需重建。
6. **核对收尾。** 刷新并清除失效的远端跟踪引用，复查本地分支、远端分支、工作树及 `git status`，报告已清理和保留的精确对象，以及回收位置或恢复依据。

远端删除形式为 `git push --force-with-lease=refs/heads/<分支>:<已核验SHA> origin :refs/heads/<分支>`；占位符必须来自刚核验的同一远端，不能照抄或拼接未经校验的名称。仅删除引用，不运行历史重写或激进 GC。已合入主干的提交继续保留在主干历史中；删除工作分支不会让它们消失。

不设置自动批量删除分支的 `post-merge` 钩子：该钩子也可能在同步上游时触发，不能单凭触发事件判断工作分支和其他会话已经结束。

Git 行为依据：[钩子](https://git-scm.com/docs/githooks)、[分支删除](https://git-scm.com/docs/git-branch)、[工作树](https://git-scm.com/docs/git-worktree)。

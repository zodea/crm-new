# 浏览器中央权威与演示工作区隔离

> 状态：已采纳（2026-08-15；2026-08-26 由 Issue #322、#323、#324、#325、#326 扩展；关联 Issue #279、父规格 #292）

> 2026-09-08 工作顺序补充：原父规格与任务组织由[全模块复核路线](https://github.com/zodea/crm-new/issues/402)承接。用户要求前台界面、交互和数据处理优先，[生产持久化、备份恢复与部署](https://github.com/zodea/crm-new/issues/416)作为后置关口；这只调整实施顺序，不取代本 ADR 的中央权威、单一写源、来源隔离与受控迁移决定。当前中央内存实例只证明功能接缝，不能以 `real` 来源身份或浏览器刷新读回宣称生产可用；既有完整账号/RBAC、多租户、Tauri 与离线写入排除仍有效。以下历史切片边界按各自决策时点阅读，当前工作清单见新路线。

## 决策

Issue #322 在两类主合同之后追加 canonical 补充协议。补充协议旧 `contract_id` 必须唯一命中施工或分包主合同的显式旧 ID 并映射为中央父 ID；缺失或同时命中两类时阻断，不按名称、编号或金额猜测。确认后补充协议取得服务端稳定 ID，并随所属合同进入同一中央命令事实源；回滚时一并撤销接管。

Issue #323 在补充协议之后追加 canonical 甲方变洽签与月度报量。迁移适配器把 BOQ 变更头/行、系统锁定台账、手录纯金额签证和月度报量头/行投影到一个逻辑 `owner_documents` 拓扑节点，但不新建平行业务表。已签证 BOQ 变更已生成的锁定台账不再作第二份单据导入；项目或施工合同旧 ID 无法唯一映射时阻断。确认后这两类正式单据的日常读写只经中央 Repository/HTTP/command；桌面端仍保留原 SQLite 路径。

Issue #324 在 #323 的两类甲方商务单据之后追加 canonical 验收—保修生命周期。`project_acceptances` 是唯一主记录；验收和保修只是同一稳定 ID 的两个读视图，不建第二张保修主表。受控迁移重验状态枚举、日期、附件分类和审计 action/from/to 合法元组，保留已有审计但不伪造缺失历史。确认后日常读写只经同一中央 Repository/HTTP/command 源。

Issue #325 继续在同一逻辑 `owner_documents` 节点中追加 canonical 甲方最终结算，不新建平行正式源。迁移把 `owner_final_settlements` 及 `owner_type='owner_final_settlement'` 的附件按稳定 ID 接管；项目与施工合同必须唯一映射，不按名称、编号或金额猜关系。`receipt_registrations` 作为结算查询的可核验一等事实节点，按项目、合同、客户稳定外键映射；合同补充协议与收款均不复制到最终结算头。审定金额和审定日为可空事实，v45 不反推存量值；本切片没有引入未证实的审定 action。

Issue #326 在同一逻辑 `owner_documents` 节点中追加 canonical 甲方罚扣，不新建平行正式源或借用项目罚扣/分包结算抵扣。迁移把 `owner_penalties` 及 `owner_type='owner_penalty'` 的联系单附件按稳定 ID 接管；项目与施工合同必须唯一映射。罚扣金额、日期、事由、联系单号、申诉说明和状态来自同一罚扣事实，申诉说明不扩展为新审批流。确认后正式列表、表单、详情与施工合同来源行只经同一中央 Repository/HTTP/command 源。

Issue #327 继续在该逻辑节点中追加 canonical 分包变洽签，但以独立 `sub_change` kind 与 `subcontract-document` capability 隔离甲方单据。迁移把 `subcontract_change_orders` 及 `owner_type='subcontract_change_order'` 的签证单附件按稳定 ID 接管；项目、分供方与 canonical 分包合同必须唯一映射并互相一致。确认后正式列表、表单、专属只读详情、项目/分供方入口与分包合同事实行只经同一中央源；分包结算、项目罚扣及未实现审批流不因此接入。

受控快照随 canonical 施工合同嵌套完整 BOQ 目录和尚未成单的月度完成量事实，避免只从历史变更/报量明细反推时丢失“首张变更”和“新期次报量”的正式命令候选。这些嵌套事实不新建平行业务表，也不扩展到其他 BOQ 工作面。

当前生产客户端只交付浏览器。已迁移领域的正式业务事实以中央服务为唯一权威，浏览器页面经领域 Repository 与 HTTP adapter 读取；服务端会话注入稳定 `workspaceId`、`actorId` 与 capability，客户端不能声明操作者或把前端布尔值当权限。尚未迁移领域的 `production` 快照只是过渡期本地投影与写入暂存，不冒充中央事实。

核心身份链的浏览器切换由 #294 落地：客户、分供方、班组、项目、工人、项目分供方必须按明确操作完成预检、不可变备份、dry-run、拓扑导入、对账和确认，不能在启动时静默迁移。#320/#321/#322/#323—#327 依次追加 canonical 施工合同、分包合同、补充协议、五类甲方单据与分包变洽签；各实体都依明确稳定外键映射。本地迁移适配器必须从受保护字节重算摘要、来源哈希与版本，创建和恢复时都拒绝不一致；正式导入和确认前还要重新读取当前 `production`，发现备份后变化即阻断，确认前的中央待确认批次须先撤回。服务端重算 canonical 来源哈希、验证备份证明结构，并将其不可替换地绑定同一批次。浏览器整库备份不上传中央，故后台不冒充能够读取 IndexedDB 原始字节。导入后服务端还须从实际中央状态重新对账，不能信任客户端门禁或导入前计划代替事实。确认后，已接管实体的正式读写以中央 HTTP/Repository/command 为唯一入口；确认命令将迁入事实接管到同一中央命令源，回滚命令则按备份边界撤销该接管。旧 `production` 快照的普通读取和写入均被阻断，只能由迁移适配器从受保护备份恢复。当前中央端是沿正式 HTTP/Repository 接缝运行的可重置测试实例，用来证明身份、权限、映射、对账与回滚；它不是生产持久化业务库的声明。

正式与演示数据使用不可互换的来源身份。读 DTO 暴露只读 `dataOrigin='real'|'demo'`；详情按服务端校验的 `(dataOrigin, id)` 解析，URL 中的 origin 只是请求意图，不能把演示记录重新标成正式记录。查看演示数据必须同时满足用户显式开启 `includeDemo` 和后台 capability。

尚未迁移到中央服务的浏览器读面使用两个隔离的本地快照：`production` 快照只运行迁移、不自动 seed；`demo` 快照才运行确定性 seed，并在初始化后以只读驱动暴露。全局演示授权由服务端 `demo:read` capability 判定；本地偏好只能表达请求，伪造偏好不能开启 demo 快照、通知或业务候选。切换前必须确认已保存所有页签内容；确认后用一次性待切换标记重载，只有新应用实例完成服务端授权后才提交偏好，使所有 Pinia 投影、通知、本地数据库连接与 Lookup 最近选择同时换到对应边界。静态通知样本同样只在授权后的演示模式可见。

测试叠加只用于查看。演示详情、关联和本地快照不得进入正式新增、编辑、审批、付款、归档或删除命令；对于已携带 `dataOrigin` 的来源感知关联，只有目标页已消费同一来源策略才可链接。否则无论来源是 `real` 还是 `demo` 均退化为普通文本，避免中央正式关系误入演示快照，或演示关系误入正式本地页。未携带来源身份的既有本地关联仍按原导航矩阵处理。

## 后果

Issue #323 的历史边界是只追加甲方变洽签与月度报量，#324 再追加验收—保修，两者都不被本决策回写为当时已覆盖最终结算。Issue #325 单独追加最终结算及其收款事实；#326 单独追加甲方罚扣。Issue #327 现单独追加分包变洽签，且不扩展分包结算、项目罚扣、抵扣或其他 BOQ 工作面。

- 正式浏览器首次打开不会因任一空表自动灌入 JSON、工程量、BOQ 或排程样本。
- 关闭开关时，中央查询、尚未迁移的本地业务读面和通知角标都不显示演示数据；开启后应用壳持续显示测试数据状态。
- Lookup 最近选择按 `(workspaceId, dataOrigin)` 分区，演示候选不会回流到正式工作区。
- 正式与演示可以拥有相同 ID、名称、编号或金额；分页稳定键使用 `(dataOrigin, id)`，汇总按来源分别计算。
- 旧浏览器整库快照不自动升级为正式事实。#294、#320—#327 对六类核心身份、canonical 施工/分包合同及其补充协议、五类甲方单据与分包变洽签提供显式的备份、稳定 ID 映射、父引用映射、导入、对账、确认接管与回滚；其他领域的迁移仍按各自切片推进。
- 切换记录含批次、来源哈希、备份 ID、确认时间和回滚截止时间，刷新后仍须与中央活动批次相互校验。若本机标记与中央权威不一致，客户端必须停止并显示错误，不得回退到旧库继续提供正式数据。
- 普通客户、分供方、班组、工人和项目分供方页面的中央读写接线不属于 #294；由 #281 在不破坏本切换边界的前提下逐页接入。项目列表和基础详情已可读取已确认导入的项目身份。
- Tauri 正式交付、完整登录/RBAC、多 workspace 切换和演示编辑产品不在本决策的当前实现范围内；桌面壳不显示也不消费浏览器演示开关，始终连接原有 `sqlite:crm.db`。

## Issue #328 扩展

分包结算现经同一中央 Repository/HTTP/command 源读写；受控迁移接管统一支出结算和结算单附件，不建平行正式源。详情和显式编辑分离，确认后成为真实候选。项目罚扣执行、整改与抵扣审计仍由 #329 承接。中央测试实例的持久化限制与本 ADR 原有声明不变，业务细节只见[页面蓝本](../rewrite/pages/owner-documents.md#issue-328-分包结算中央只读链)。

## AX03 项目罚扣接管

Issue #329 在同一逻辑 `owner_documents` 节点追加 `project_penalty`，接管 `penalty_records.source='project'`、罚扣附件和独立抵扣事实；责任班组、分包合同及真实结算全部按显式旧 ID 映射。浏览器列表、表单、详情、班组/合同来源行及抵扣/整改命令只走同一中央源。中央追加记录支持同结算多次部分抵扣；旧 SQLite 唯一关系不成为第二套日常正式源。具体余额、候选和审计字段只以 [DATABASE](../rewrite/DATABASE.md#ax03-中央项目罚扣与独立抵扣事实) 为准。本次不改变可重置测试实例的部署边界。

## AX04 辅助合同接管

Issue #330 追加逻辑 `auxiliary_contracts` 节点，分别接管项目其他支出与公司支出合同。两类旧 ID 按类型加命名空间后映射，项目合同只关联真实项目和分供方，公司合同无项目关系。确认后浏览器正式列表、详情与显式表单只经同一中央 Repository/HTTP/command；旧本地源不得并行提供日常正式读写。Tauri 原列表和表单仍保留原路径，本票不声明桌面中央交付。接管包括已有附件元数据与按显式外键取得的票款、结算和增补投影；不复制无依据的业务明细或审批轨迹。具体字段和聚合口径仅见 [DATABASE](../rewrite/DATABASE.md#ax04-辅助合同中央事实)。可重置测试实例及文件内容服务的现有边界不变。

## AX05 其他支出结算接管

Issue #331 在辅助合同后追加 `other_settlements` 迁移节点，物理来源仍为统一 `expenditure_settlements`。浏览器结算列表、专属详情与整页表单统一经中央 Repository/HTTP/command；合同中的结算投影也读同一结算源，不保留辅助合同内的第二份正式结算快照。迁移按项目、分供方与带类型命名空间的合同稳定外键接管，试跑检查源合同关系、事实及附件元数据。具体口径见 [DATABASE](../rewrite/DATABASE.md#ax05-其他支出结算中央事实)。本票延续可重置测试实例和附件元数据边界。相关付款申请及支付记录通过 `other_settlement_sources` 独立接管，罚扣复用既有中央项目罚扣；源单与父申请 ID 经迁移映射，下钻单独读取中央资料。源单删除、权限不足或关系失效时明确显示原因。

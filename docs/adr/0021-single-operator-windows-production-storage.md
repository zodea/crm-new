# 单人 Windows 正式存储与可验证备份

> 状态：已采纳（2026-09-22）；生产实现与上线验收尚未完成。来源：[部署决策 #416](https://github.com/zodea/crm-new/issues/416)及本轮用户回答。继承 [ADR 0020](./0020-browser-authority-and-demo-workspace-boundary.md)，不改变业务事实归属。

用户首期独自使用并维护现有可常开 Windows 电脑，没有另购服务器；单人本机先落地，后续同事接入时再保护内网入口，异地访问后续处理。业务记录和附件一起恢复的目标为最多丢失 1 天（RPO ≤ 24 小时）、1 个工作日内恢复（RTO ≤ 1 个工作日）。用户已有 NAS、移动硬盘和另一台电脑。本期采用本机中央服务、单一磁盘 SQLite 权威库、NAS 主备份与移动硬盘离线副本，以降低运行组件数量和跨存储一致性成本；不用重做已完成前台流程。

## 正式存储与运行边界

- 首期仅绑定 `127.0.0.1`，不开放同事内网和公网入口。由 Windows 计划任务启动固定发布物，任务失败、休眠后错过备份及重启恢复均进入验收。开发目录、发布目录、正式数据目录、备份和访问密钥分别管理。
- 使用已存在的 Node `24.12.0` 内置 `node:sqlite`，当前 SQLite 为 `3.50.4`，无需新增 npm 生产依赖。该确切版本 API 仍带实验标识，封装在窄 `DbDriver` 边界并固定版本；升级须先在备份副本验证迁移、回执、原件、恢复和构建兼容，不无条件升级。接口依据见 [Node 对应版本文档](https://nodejs.org/download/release/v24.12.0/docs/api/sqlite.html)。
- 数据库位于本机磁盘，不把活动数据库放 NAS/同步盘。已有 SQL 事实与其他领域聚合、版本、审计、迁移接管状态、命令指纹和回执纳入同一持久事务边界。现有 `Map` 只能是提交后可重建的投影；不会成为平行权威。正式模式缺目录、无法写入、数据库损坏或版本不兼容时明确拒绝，绝不回落空内存实例或旧浏览器库。
- 原件首期以同库 BLOB 保存，保持领域 owner、稳定 ID、摘要、历史版本及私密权限。这样一次数据库一致备份包含业务和原件，避免文件目录与数据库分开复制造成错配；代价是数据库和备份可能较大。必须测代表性最大原件、并发读取、备份时日常写入、容量不足及恢复耗时；不承诺无限容量。将来若改外置原件，另行规定发布、清单和回收协议。
- 保存成功须在可靠提交后返回。业务事实、原命令结果和原件同事务；重启后重复原键不重复付款、发放、扣款或导入。锁与事务配置、日志/同步模式须明确并经故障测试，不能拿进程退出测试冒称物理断电/设备故障已通过。

## 单一维护人身份

单人本机仍使用访问码建立服务端会话，操作者使用服务端持久配置中的唯一 owner 身份；密钥不入仓库、URL 查询串、日志或前端持久化。正式模式缺访问码或身份配置须拒绝启动为可用状态。凭据验证、会话过期/注销、跨站写入保护、测试头绕权、来源隔离和原件读取均须验收；仅已认证的 owner 会话可获得所需的私密读取能力。客户端不能提交任意 actor 或 capability。

此处只建立单人入口和可信审计，不新增完整账号管理/RBAC、多租户、审批引擎或离线写入。后续多人/内网访问必须重新核对入口认证、权限分配、个人审计和容量，不能直接把监听地址改成全部网卡后声称完成。

## 备份与恢复

- 使用数据库一致备份接口生成隔离副本，核对完整性、外键、参与领域清单、数据/原件摘要及版本后，才将其标为可恢复备份；不直接复制运行中的活动库。依据见 [SQLite 备份接口](https://www.sqlite.org/backup.html)。
- NAS 为主备份目标，移动硬盘为离线副本。实际路径、NAS 权限和凭据在部署配置中核实，不写进仓库或要求用户在对话公开。备份只向本人受控位置写入；失败或介质缺失不得覆盖最后一份已验证备份。离线副本记录自己的最近成功时间。
- 技术默认值：每 12 小时尝试主备份、应用启动/恢复后补跑错过的备份；保留 30 份日备份和 12 份月备份，均可配置。清理只针对本工具生成、完成校验且超保留策略的备份，不碰其他文件；保留最后一份可恢复副本。具体离线复制步骤和频率在运维指南明确。
- 计划频率不等于已经达到 RPO。距最近已验证独立介质备份超过 24 小时、无法连接 NAS、空间不足或校验失败时，应用内持续明确显示保护已失效、最后成功时间和恢复动作，由用户本人处理；不能只弹一次 toast。关机/断电期间无法备份须如实登记，重新运行后补跑仍不能抹去此前保护失效。
- 首次正式写入前，须完成至少一份独立介质上的可验证基线备份并准备好恢复方式；在隔离位置完成基线恢复检查。正式上线验收另以完整业务与原件数据集证明 RPO/RTO，不能只用空库演练宣称全域恢复通过。
- 恢复先到隔离目录，验证版本、业务数量/金额/关系、原件摘要、回执和接管状态，通过后才切换。灾难恢复、业务迁移回滚和发布回退分别有前提和停止点；不得借备份覆盖绕过已有工资/迁移引用保护。

## 验收与承接

实现按[实施承接入口](../implementation/production-gate-work-breakdown.md)形成可独立演示的生产子票。备份工具可先对客户首条持久化路径开发，全域恢复验收最后等待全部交付参与者；不把所有领域开发串成备份工具的开工条件。#416 决策关闭和后续实际上线通过分别记录。

本方案选择现有运行时和本机存储，避免首期单人使用额外维护独立数据库服务器；选择同库原件降低一致性复杂度，同时明确容量代价。运行约束改变时重评，不把本期方案泛化成多用户或公网部署方案。

# 工程量矩阵与施工记录模型：户型模板活链接 + 量/完成分层 + 完成勾选四合一 + 施工记录派生

> 状态：已采纳（2026-07-08，grill 定稿）
> 影响：`DATABASE.md`（新增 `house_type_templates` / `house_type_template_items` / `unit_assignments`，`units` / `projects` 调整，`quantities` 重构拆分）、`docs/rewrite/pages/subcontract-quantity.md`（工程量管理蓝本大改）、`CONTEXT.md`（户型模板 / 工程量指派 / 完成勾选 / 施工记录 词条）、[#73](https://github.com/zodea/crm-new/issues/73) §8（施工记录迁移落点）、工程量矩阵/工资/进度相关实现。

## 背景

原设计假设工程量是一张 `quantities`（分项 × 房间 × 工人）合一表，工资工具**只读**它、**自动**按施工人聚合，施工记录只是它的「工人视角」、与矩阵「双向同步」的纯派生视图。2026-07-08 与用户 grill 后，这套假设在三处与现场实际脱节：

1. **量按户型、不按户**：同户型（A/B/C）的户量一样，现场**没时间逐户复测**——同户型只有一种现场量（现场复核计算式）。原「每户 × 分项」存量是重复。
2. **完成有人工整理环节**：现场施工员在**发工资前**要人工整理「这个月谁做了哪些户 × 工种」——不是指派 + 勾选就能全自动聚合出来的。用户原话：「工程量清单是每次派发工资前才做的一次整理」「施工记录会有现场施工员的整理」。
3. **同工种多班组**：一个工种（如泥水）可能有多个班组（泥水 A 班做低层、B 班做高层），指派要支持按区域分工，原「每分项配一个施工人」不够。

## 决策

**工程量矩阵是一个深模块**：写入面很小（户型模板配置 + 现场「勾房」一个动作），背后的施工记录、工序进度、月度报量、工资进度清单全是坐在读 seam 上的**派生查询、不各自落表**。据此定七条：

1. **户型模板活链接**：项目内每个户型（A/B/C…）一份「房间 × 工种/分项 × 三量」模板；一个模板挂多个同户型的户，**改模板 → 挂靠户的结构/清单量/暂估量/现场量实时跟着变**（镜像户型归并的实现）。新建模板可**借用**另一模板一次性快速填充（快照复制、非链接），编辑为**草稿**、**保存才提交**生效。
2. **量在户型层、完成在户层**：三量（清单量 / 暂估量 / 现场复核算式）落 `house_type_template_items`，**同户型共享**；完成 / 指派 / 月份落 `unit_assignments`，**逐户记**（同户型不同户可由不同班组、不同月做完）。
3. **清单量双通道 + 留痕**：有合同清单 → 从 `boq_lines` 按户型读入；无清单 → 手动填。**任意一档量都可手改**（清单识别可能不准），手改清单量保留「识别原值 ↔ 手改值」对照，服务量差口径。
4. **完成勾选四合一**：现场唯一登记动作 = 在「人/班组视角」勾一个房，一次完成「指派谁做 + 标记完成 + 记月份（默认输入月、可改）+ 落该工种量」。取代原独立的「完成勾选」。提交时缺[[验收照片]]则弹「取消 / 保存到草稿」（软卡点防丢，非硬锁）。工序进度 = 已勾户数 ÷ 总户数。
5. **指派粒度自适应**：户内先按工种拆，每工种派给**班组**（到「户 × 工种」即止）或**个人**（可按钮下钻「是否分房间」→ 房间 × 细分项，个人计件要算到房间分项量）。**批量指派**从「人/班组」视角进一张可点击的**楼层 × 房号表格**，只能勾「自己已做 + 无人做」的房（冲突房不可点），按楼层/房号分组防过载、**整层已满则隐藏**。
6. **两视角矩阵 + 极简总览**：工种矩阵（按月份颜色标进度）/ 班组矩阵（下拉切视角 + 月份切换）。总览每格只标「是否有人施工」，hover 蒙板 → 右上进配置、右下进详情页。
7. **施工记录 = 派生详情视图，不独立导入**：户/块详情页展示「工种 × 月份 × 做了什么」，数据 = `house_type_template_items`（量）+ `unit_assignments`（完成）拼出，**不落表、无独立导入模板**。**工程量矩阵本身有导入/导出/归档**：导入走 [ADR 0005](0005-import-mapping-model.md) import-mapping（历史/批量按模板字段录入）、导出走 [ADR 0004](0004-export-interaction-model.md) 全局导出规范、录入完点**归档按钮**锁定为不可编辑（改走二次确认）。

## 考虑过的替代

- **维持 `quantities` 合一表、不拆**（否决）：无法表达「量跟户型、完成跟户」的分层，同户型的量要在每户重复存 N 份，改一处要手改 N 处——正是活链接要消除的漂移。
- **施工记录建独立实体 + 独立导入模板**（否决）：红圈 `constructionReport3X` 是「按天施工日志」（天气 + 当天干了啥），与瑞航「工人视角区域明细」口径完全不同，字段 95% 靠推断；施工记录本质是 template_items + assignments 的派生视图，没有独立旧表可导。
- **户型模板做快照、非活链接**（否决）：用户明确要活链接——同户型改一处、所有户跟着变；快照会让「后期调模板」退化成逐户重改。（现场量本来就同户型一种，也无逐户独立的必要。）

## 后果

- **[#73](https://github.com/zodea/crm-new/issues/73) §8 定案**：施工记录**不设独立导入模板**；历史「谁做多少量」随工资历史迁（#73 决策：全迁），在建 + 已完成项目都录入矩阵、已完成项目归档锁定。
- **`quantities` 重构**：拆成 `house_type_template_items`（量）+ `unit_assignments`（完成/指派/月份），动到已落地的软删除 store（`quantities` 相关），迁移随工程量域批次 PRD。
- **派生 vs 快照**：施工记录 / 工序进度 / 月度报量是**实时派生查询**；**工资进度清单**发放前是派生预览、点「确认发放」时**快照**进 `wage_statement_lines` 固定，之后矩阵改动不影响已发工资单。
- **深模块的回报**：一份写入（模板 + 勾房）供 4 个读视图复用（leverage），量差/工资/进度口径的改动收在这一个模块内（locality）；调用方（工资/进度/报量页）只学「读矩阵」这个小接口，不碰底层 template/assignment 拆分。
- 表格三件套仍走 [ADR 0009](0009-vxe-table-as-datagrid-engine.md) KitTable；矩阵本体是自研的可点击网格（非数据表格），与 KitTable 正交。

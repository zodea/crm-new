# 表单字段持久化与付款申请勾稽：可编辑默认入库 + 真实关联分摊

> 状态：已采纳（2026-07-19，grill 定稿）
> 影响：ADR 0014 整页表单、`DC重构设计源码/kit/forms/*.jsx`、`docs/rewrite/DATABASE.md`、`docs/rewrite/pages/finance-payment.md`、issue #116。

> 后续适用边界：本 ADR 保留 2026-07-19 的决策依据、原范围和示例；下文“三类”等表述不作为当前完整规则。现行字段、关系、票款计算及工人工资例外直接以 [`DATABASE.md`](../rewrite/DATABASE.md)为权威，公共保存、原子提交、回执和恢复以 [`COMMANDS.md`](../rewrite/COMMANDS.md)为权威；[付款页面契约](../rewrite/pages/finance-payment.md)只维护交互及领域操作。浏览器已迁移领域的数据归属按 [ARCHITECTURE](../rewrite/ARCHITECTURE.md#read-write-boundaries)，[ADR 0020](./0020-browser-authority-and-demo-workspace-boundary.md)保留相应裁定依据，不向本地 SQLite 建立平行正式写入，也不以本 ADR 的“默认持久化”原则代替实际保存验收。

## 背景

ADR 0014 已把 37 个业务对象的新增/编辑表单补到字段级，但旧 schema 只覆盖其中一部分；若继续逐字段讨论“要不要存”，容易让设计稿可编辑、刷新后却丢值。付款申请中的 `settleLinks` / `invoiceLinks` 还只是自由文本行，既不能追溯源单，也无法阻止超额关联。

## 决策

1. **用户可编辑的业务字段默认持久化**：标量落实体列，lookup 落真实外键 ID，明细 grid 落子表，file 落 `file_refs`。例外只允许显式列出：`readonly + compute`、`_` 前缀展示字段和纯聚合不存；人工核验等具有审计价值的结果即使可计算也要存。草稿允许业务列为空，提交态再按业务规则校验。
2. **领域语义高于控件外观**：分供方继续遵守 #13 已定语义——注册地址与开票地址分离，纳税人默认未核验，`qualified` / `rejected` 必须有人工审核凭证。设计控件不能把这些约束降级为普通文本或默认已通过。
3. **付款申请—结算是真实分摊关系**：分包、材料采购和其他支出合同的过程/完工结算统一进入 `expenditure_settlements`，它才是付款申请可选择的真实源单；`project_suppliers` 下 1:1 的 `settlements` 只表示合作关系终态关闭，不参与付款勾稽。`payment_application_settlement_allocations` 只存付款申请 ID、真实支出结算 ID、本次关联金额和备注；结算单号、名称、含税结算金额从源结算读取。有合同的三类付款申请提交时必须满足 `Σ 本次关联结算金额 = 申请金额`；草稿允许不平，但必须显示差额。预付款、公司付款等没有关联结算区的类型不套此规则。
4. **付款申请—发票按回票类型勾稽**：`payment_application_invoice_allocations` 只存付款申请 ID、真实发票 ID、本次关联金额和备注；票号、开票日期、含税金额从 `invoices` 读取。`先票后款` 提交时必须满足关联发票金额合计等于申请金额；`先款后票` 可无票提交并持续显示派生的待回票金额，后续补关联；`无需发票` 隐藏/禁用关联区且不得存在关联行。同一发票跨全部付款申请的有效关联金额合计不得超过其含税金额。
5. **银行流水是合同及一般付款的实际支付唯一事实来源**：一张银行账单或银行回单只形成一条 `payment_records` 支付记录，不因对应多份付款申请而拆分或复制。支付记录与付款申请通过 `payment_record_application_allocations` 建立多对多金额分摊；一份付款申请也允许分多次支付。确认支付时，分摊金额合计必须等于支付记录金额。付款申请的累计已付与实际支付均由有效支付分摊实时派生，不再作为可编辑金额维护。工人工资是显式例外：工资单“确认发放”本身即支付事实，不要求为大量工人逐笔建立银行回单或支付分摊。
6. **图片识别只负责预填支付事实**：支付金额、日期、收款方、银行流水号等优先从银行回单图片识别；识别失败或字段缺失时允许手工填写。无论来源为何，金额都表示银行凭据上的实际支付，不得从申请金额、批复金额、合同金额或文件名反推。OCR 结果无论置信度多高都必须人工核对并明确确认；未确认记录不得参与合同付款、付款申请累计已付、项目支出或资金余额。

## 后果

- Issue #116 已完成逐实体 schema 评审：37 条表单的列名、类型、约束、真实外键、子表和 F1-F5 迁移批次见 [DATABASE §2 逐实体定义](../rewrite/DATABASE.md#-2-全部实体清单)及 [§2.10 表单覆盖与来源批次](../rewrite/DATABASE.md#210-整页表单覆盖与来源迁移批次)；旧蓝本中的 #116 警示横幅已移除。该定稿不等于迁移、store 或 Vue 页面已实现。
- 付款申请保存 action 必须在一个事务中写申请头与两类分摊行；提交校验和发票全局额度检查也在该 action 内完成，页面不维护自由文本副本。单票额度以 `invoices.total_amount`（含税金额）为上限，不得误用不含税额 `invoices.amount`。
- `待回票金额 = max(申请金额 − 有效发票关联金额合计, 0)` 为派生值，不另存列。
- `payment_records.amount` 是支付金额唯一落点；`payment_applications.paid_amount` / `actual_payment` 退出手工写入路径，读取时按有效 `payment_record_application_allocations` 汇总。迁移前的存量手写值只能用于差异核对，不可覆盖银行流水。
- 支付记录 OCR 结果需保留来源与识别状态，人工修正后以修正值作为当前业务值；银行回单文件通过 `file_refs` 关联支付记录，不在多份付款申请下重复保存。
- 支付记录至少区分“待识别 / 待核对 / 已确认”；只有“已确认”是有效资金事实。全绿识别结果可以标记为建议确认，但不得自动确认或自动进入汇总。
- 工人工资进度款按 #117 确认发放后形成唯一工资支出事实，并在同一动作中同时形成工资成本与工资已付；这里的支出事实由原工资发放投影，不另生成 `payment_records`、付款申请或往来款副本。独立实际补退及有依据的错记冲销由工资域记录；仅核算更正及后月处理关系不重复计作现金。不要求银行回单，不等同于本 ADR 的合同付款申请—结算/发票勾稽；具体来源规则见 [DATABASE](../rewrite/DATABASE.md#工资更正实际补退与后月处理412p4)。
- 工资发放产生的税额以及我方开具票据的方向和归集规则不在本次决策范围；在后续业务口径明确前，不自动生成销项或进项票据，不纳入本次迁移映射。

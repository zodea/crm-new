# 导出交互模型:直接保存 vs 配置导出页签

> 状态：已采纳（2026-07-04；2026-07-13 补充直接保存运行环境约定）

「全局导出规范」要求所有模块共用一套交互口径,但并不要求所有导出都先配置目录。若一律塞进居中弹窗,会遮罩挡住用户想边导边看的信息,且提交失败或点遮罩外易误触关闭;无需目录分类的导出若也套完整配置,则是杀鸡用牛刀。原「完成水波动效」方案已随全局水波废弃一并取消。

**决策**:导出按「**导出前是否需要配置目录结构**」分两条路。

1. **直接保存 (`direct-save`)**:无需目录分类时,点导出直接选择目标文件夹并写入。不开页签、无配置 UI;单文件只是典型场景,不是分流条件。
2. **配置导出 (`config-tab`)**:需要目录分类时(如批量导出分供方合同、采购合同),点导出打开**独立「导出配置」页签**——两级文件夹结构 + 命名规则 + 带预览,点开始后**在同一页签内**转进度(进度条 / stepper:读数据→生成→写盘)。文件数同样不是分流条件。

**直接保存的运行环境约定**:

- Tauri 桌面端使用系统目录选择器,选定后真实写入磁盘。
- 浏览器优先使用 File System Access API 选择目录并写入;环境不支持时退化为浏览器下载,落点如实显示为「浏览器下载」,不得伪装成本机绝对路径。
- 用户取消目录选择时静默结束,不显示成功、失败或取消 toast。
- 写盘期间只显示右下 process 道 loading;成功后 dismiss 该 loading,不得把它转成 process success。
- 最终唯一成功反馈是右上 system 道 toast:「已导出到 X 文件夹」,其中 X 是用户选择的目录或「浏览器下载」。不叠加其他成功反馈,不播放 ripple 或其他完成动效。

**统一约定**:

- **完成落点 = 唯一 system 道成功 toast**,文案固定为「已导出到 X 文件夹」,**无任何动效**。
- 配置 UI 只做这一套(在页签里),所有需配置的导出复用,不重复造。
- 导出配置页签**算 [[页签导航]] 15 上限**,成功后**自动关闭**;失败保留该页签、标明失败步、可重试。
- 直接保存的写盘等待轻走右下 process 道 loading;配置导出的多阶段进度在页签内。失败可在原载体转 error,但成功反馈不得重复。

**考虑过的替代**:

- 全部走居中配置弹窗(遮罩挡信息、提交失败/点外误关,否决——正是改用页签的动因)。
- 单文件也套完整配置弹窗(过度、且要维护多套 UI,否决——改直接弹系统文件夹选择器)。
- 完成播蓝色水波动效(CSS 版效果差、GIF 版性价比低,全局废弃,改静态 toast 成功)。

**后果**:

- 判定分流的钥匙是「是否需要目录分类」,不是文件数多少——需分类即开页签,不需分类即直接存。
- 导出配置页签是一个可被任意模块打开的通用路由(带导出上下文参数),不是每模块各写一个。
- 「导出配置」页签受 15 上限约束,与列表/详情页争额度,故必须完成即自动关闭,避免长期占位。
- 为直接保存新增最小 Tauri 2 shell、目录选择与文件写入能力,只代表桌面运行底座就绪,**不代表已发布安装包**;安装包构建与发布仍是独立交付范围。

# 标准工序库采用不可变版本与可恢复的前置关系

> 状态：已采纳（2026-07-29）
> 来源：用户确认“标准工序库独立维护、建组时甘特拖拽、冲突关系先置灰不删除”

## 决策

标准工序库通过 `/schedule/process-library` 独立维护。既有版本一律只读；新建空白库产生 v1，基于旧版调整只能沿用原 `code` 新建下一版本，不能原地改写或跨编码复制。建组时继续冻结库名、版本与工序快照。

每道库工序保存名称、工种、默认工期、阶段/分项映射和一个前置关系。前置选择使用行级轻量弹窗，只列计划日期更早的候选。整页表单的甘特和精确表格共用同一份任务草稿：拖整条调整顺序或锚点，拖右缘调整工期。

调整导致前置错序时必须先确认。取消不改变草稿；确认后保留 `predecessor_task_key`，只将 `predecessor_disabled=1` 并置灰。顺序恢复后用户可显式重新启用。建组时禁用关系仍写入 `task_dependencies`，随后用 `operator=schedule:conflict-reschedule` 软删除，确保项目内可审计、可恢复。

## 后果

- 快速切换工序库采用 latest-request 守卫，旧响应不能覆盖新选择。
- 未置灰的后续工序不得早于前置工序开始；领域 action 再次校验，不能只依赖界面。
- 标准库版本和项目排程都保留冲突关系身份，不以清空外键制造“看似正常”的计划。
- 版本列表、表单和建组第二步在窄屏只允许各自表格/甘特区域横向滚动。

## 迁移边界

已应用迁移保持不可变：v34 只增加 `predecessor_task_key`、回填既有版本的顺序前置并创建索引；`predecessor_disabled` 由 v35 单独增加并把空值或非法旧值回填为 `0`。因此数据库即使已经登记 v34，也会在升级到 v35 时补齐禁用状态列，不能通过修改同一 v34 或清空本地库规避升级。

# OCR 引擎：PaddleOCR-VL 单模型，本地自托管为主、云端官方 API 显式启用

> 状态：**已采纳**（2026-07-05 草案；2026-07-06 用户逐条重新拍板确认；2026-07-16 用户授权先接官方线上 API，用真实样本评估识别质量）
> 本版**取代**初版的"三层多引擎（PP-OCRv6 + 本地文本LLM + 独立视觉LLM）"方案——收敛为单一 PaddleOCR-VL。

> 后续边界：本文保留当时的引擎选择、硬件与样本评估，版本“最新”、性能比较和本地后端设想均按该时点阅读，不作为当前运行可用性证明。本文只裁定 OCR 路径，不能用其中“财务数据默认全本地”的历史描述覆盖后来 [ADR 0020](./0020-browser-authority-and-demo-workspace-boundary.md)的浏览器中央业务权威。当前 OCR/文件能力按[文件流程复核](https://github.com/zodea/crm-new/issues/406)验证，实际部署由[后置生产关口](https://github.com/zodea/crm-new/issues/416)承接；既有云端显式启用、凭证只留服务端和人工核对边界继续有效。

用户是工程财务管理员，处理真实发票/送货单（含税号/金额/公司名），三诉求叠加：**成本敏感**、**隐私敏感**（数据不愿外传）、**要打磨质量**；环境 **Windows 为主**（主力机 Ryzen 5 5600 / 16GB / RTX 4060，2026-07-06 实测确认），**Mac 需可用**（初版调研误设 macOS 为唯一环境，已更正）。已有一套跑通的实现（`invoice-recognition-app`），其 `ocr-vl.js` 已集成 aistudio 的 PaddleOCR-VL 云端异步 job API（模型名 `PaddleOCR-VL-1.6`）。初版曾设计"本地 PP-OCRv6 + Ollama 文本 LLM + 独立本地视觉 LLM"的三层多引擎方案，但多模型在一台 Mac 上争内存、需切换/加载卸载调度（keep_alive、OLLAMA_MAX_LOADED_MODELS），复杂且易互相干扰。

**决策**：OCR 识别用**单一 PaddleOCR-VL（0.9B 多模态模型）**做引擎，一个模型完成 OCR + 表格 + 公式 + 手写 + 版面结构，图 → 结构化 Markdown + 版面区域；再由**规则正则**（现成 `vl-parse.js`/`invoice-parse.js`）在 Markdown 上抽出发票/送货单字段。

- **模型版本**：默认 **PaddleOCR-VL-1.6**（最新，0.9B，含发票/边框表与手写强化；与源项目 `ocr-vl.js` 已用的版本一致）；1.5 为已验证稳定回退。全系同为 0.9B，无尺寸取舍。
- **部署（主）= 本地自托管，首选 `llama.cpp`**（2026-07-06 定：Windows 为主 + Mac 需可用，取跨平台通吃的后端）：Windows 走 CUDA 构建（RTX 4060 8GB 跑 0.9B 富余），Mac 走 Metal 构建，同一套 GGUF 模型文件、同一个本地 server 协议，前端零分支。**MLX-VLM 降为 Mac 专属可选加速**（<14B 比 llama.cpp 快 20–87%，仅当 Mac 侧成为常用环境再启用）。Apache-2.0、数据 100% 不出机器、可离线、零泄漏。0.9B 极轻，硬件门槛远低于 7B 级模型。
- **部署（显式启用的评估/联网模式）= PaddleOCR 官方 API**：2026-07-16 起先接官方异步 job API（`PaddleOCR-VL-1.6`），用于真实样本质量评估和本地运行时就绪前的识别。真实票据会上传至百度服务，必须由用户明确启用并自行配置 Access Token；不做静默上传或自动回退。浏览器只调用同源 Nitro 代理，Token 仅由服务端环境变量读取。当前该模式用于浏览器 dev 验收；若后续把云端定为生产能力，需另立工作项实现受控远端代理。
- **结构化**：规则正则（A）为主（VL 的干净 Markdown/表格让正则更稳）；本地文本 LLM（Ollama qwen2.5）降为**可选的极个别怪版式兜底**，默认不启用、不常驻。
- **统一识别接口** `recognizeDocument(file) → { markdownPages, pages[{ layoutRegions }], engine, model, jobId }`；发票/送货单分别在本地纯解析器中把 Markdown 转成领域字段，引擎（本地 VL / 云端 VL）切换不渗透到页面和 store。
- **坐标/高亮**：PaddleOCR-VL 输出版面区域（layout regions），支撑"点字段↔高亮原图"（块级）；参考实现 `CHEN010325/paddleocr-local` 已展示原图对齐可视化。

**考虑过的替代**：

- **三层多引擎（本地 PP-OCRv6 + Ollama 文本 LLM + 独立本地视觉 LLM）**（初版方案，否决——三个模型在一台 Mac 上争内存、需加载/卸载切换与 keep_alive 调度，复杂且互相干扰；单一 0.9B VL 一个模型全包，复杂度清零）。
- **云端 aistudio PaddleOCR-VL 静默作为生产主力**（否决——数据到百度云、必联网、免费额度/队列不可控；仅允许用户显式开启的联网模式，本地自托管仍是最终默认）。
- **源项目本地 `@paddlejs-models/ocr`**（否决——旧小模型、无坐标无表格、质量弱）。
- **视觉大模型云 API（qwen-vl / gpt-4o / Gemini）**（否决——虽然便宜（~$0.0003/张），但数据出机器、泄漏面大；本地 VL 质量已 > GPT-4o 且零泄漏）。
- **PP-OCRv6 传统管线（检测+识别）**（否决——不返回版面/表格语义、要额外结构化层；VL 一步到位）。

**后果**：

- **架构大幅简化**：从三层多引擎收敛为"一个 0.9B VL 模型 + 规则正则"，**"多模型互相干扰"问题消失**，无需 Ollama 内存调度/模型切换。
- **隐私满足**：本地自托管数据不出机器、可离线、零泄漏；财务数据默认全本地。
- **质量满足**：PaddleOCR-VL 文档解析 > GPT-4o（OmniDocBench，1.5 达 94.5%），印刷发票 + 手写送货单一个模型覆盖。
- **硬件门槛低**：0.9B 极轻（远小于 7B）。主力 Windows 机已确认（Ryzen 5 5600 / 16GB / **RTX 4060 8GB**）：CUDA 跑 0.9B 显存富余，**无需激进量化**（Q8 或 FP16 均可）。Mac 机型待有需要时再确认（届时才涉及 MLX 加速与量化档位）。
- **移植受益**：源项目 `ocr-vl.js`（VL 异步 job 协议）+ `vl-parse.js`（Markdown→字段）直接复用；本地端点只需把 base 指向 MLX/llama.cpp 本地 server，删掉云端 Tauri/vite 代理分支。
- **开发与质量评估提速**：可先用官方 API 跑通真实识别和建立样本准确率基线，再切本地自托管；两端继续遵守统一识别接口。
- **待验证**：本地 PaddleOCR-VL 对中文潦草手写送货单的实际质量需抽样实测（手写仍是全行业分水岭，保留人工复核）；VL 版面区域到"发票字段级"高亮的粒度需实测（块级可行，字段级看 layout 细度）。
- **凭证安全**：云端 Access Token 只存在本机 `.env` / 服务端私有 runtime config，不进入浏览器、localStorage、数据库、日志、代码或 Git；状态接口只返回“是否已配置”。本地自托管无此凭证问题。

## 2026-07-17 实施与样本核对

- 官方 API、同源 Nitro 代理、浏览器 `File` 上传边界、稳定错误码和发票/送货单两个规则解析器均已接通；Access Token 已按服务端私有变量方式配置，本节不记录任何凭证值。
- 送货单图片在浏览器内先做连通域裁白边、主轴扶正与轻度对比度增强；可解析的单页 PDF 使用 `pdfjs-dist` 以 3 倍尺寸渲染为派生 PNG 后进入同一图像预处理链。多页 PDF 和本地解析失败的 PDF 保持原文件交给 VL 文档预处理，不拆页、不合并。原文件不被改写，仍用于核对预览；图片扶正件关闭上游方向分类，PDF 派生件保留方向分类兜底。
- 真实电子发票样本：票号、日期、购销方及税号、金额/税额/价税合计和 2 条明细均可抽取，票号/销方/总额与季度台账真值一致。
- 真实旋转送货单样本：自动校正后抽出供应商、日期、普通“单号”和 10 条材料明细；解析器能区分“本页金额 3842.20”与多页“累计总计 11815.20”，本页明细求和与票面金额一致。
- 大白边、斜放、浅色手写送货单样本：原图直传时字段覆盖为 0；裁边扶正并关闭二次方向分类后可抽出分供方、日期、单号及 1 条低置信明细。手写名称/单位/金额仍可能错位，系统保留该行并标“低置信待复核”，不把它伪装成可靠自动识别结果。
- `andyhuo520/ppocrv6-studio` 采用的是本地传统 PP-OCRv6 ONNX（Tiny/Small/Medium）工作台，不是 PaddleOCR-VL 1.6 官方云 API。其透视/旋转裁剪、检测框和几何表格重建可作为后续本地引擎及调试界面参考；`model_variant`、`det_thresh`、`box_thresh`、`unclip` 等配置不得伪装成云端 VL 参数发送。

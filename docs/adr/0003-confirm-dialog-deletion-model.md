# 确认弹窗职责边界与三档删除确认模型

> 状态：已采纳（2026-07-04）
> 修订：2026-07-07——**删除一律先弹 confirm 确认**（含单条），推翻初版「单删不弹 confirm、只靠 undoToast」。见决策 1、2。

> 适用边界：本 ADR 约束业务已经允许的删除动作，不自动为每类实体开放删除或撤回。后续中央命令范围见 [`COMMANDS.md`](../rewrite/COMMANDS.md)；已确认结算、已发工资等受保护事实按各自领域的冲销/调整规则处理，不能用通用确认框和软删除覆盖其历史。

KitUI 里「软删除 + 撤回」（乐观执行、限时撤回）和「确认弹窗」（先停顿再执行）两套兜底机制并存，若不划清各自地盘，会出现该撤回的却弹确认、该确认的却只给撤回。同时 type-to-confirm（打字确认）是否值得做，取决于本域是否存在「既高杀伤又需硬停顿」的删除——软删除让几乎一切可恢复，若照搬 GitHub 式打字确认会是过度设计。

**决策**：

1. **所有业务删除一律先弹 confirm 确认**（单条 / 批量 / 级联都要，删除前统一停顿一下）；确认弹窗同样服务其他「不可撤回 / 高后果」操作（如归档后修改）。纯信息阻断（如页签上限）只弹 toast，不弹 confirm。

2. **删除按杀伤半径分三档，确认强度递增（但都要确认）**：
   - **单条删除** → 弹 confirm（simple 变体，确认删除该条）→ 点确认软删除 + 事后 **10 秒 undoToast** 撤回。
   - **批量删除** → 弹 confirm（看清「将删除 N 条」的数量）→ 点确认**立即关窗** → 事后 **10 秒 undoToast** 撤回。
   - **级联删除**（删有下游关联的父级，如分供方挂着合同/材料/发票）→ 弹 confirm 且**必须手打该记录自身名称**（如「华东建材」）才激活确认，弹窗列出杀伤清单「将影响 3 份合同、12 条材料、8 张发票」。

3. **type-to-confirm 打的是「被删记录自身的名称」**，不是固定词——每条都不同，天然防批量误删。

4. **级联删除采用「预提交挂起」而非事后撤回**：点确认后原地转 spinner、弹窗不关，进入 **≥3 秒等待期**（关联多则更久，但永不少于 3 秒）；期间显示显眼「撤销」按钮，此时**尚未写库**，撤销即彻底中止；3 秒到、未撤销才写入删除标记、关窗。**级联删除不再另给事后 undoToast**。

5. **级联的软删除只标记父级，子级靠「父级是否已删」过滤隐藏**，不逐条给子记录打标记（量太大）。一条记录被隐藏 = 自身被删 OR 其父级被删。撤回只需恢复父级，下游自动重现；删父级前已被单独删掉的子记录保持删除态、不被误恢复。弹窗的杀伤清单靠只读 count 查询得出，与删除写入无关。

**考虑过的替代**：

- ~~单条删除不弹 confirm、只靠 undoToast~~（初版设计，2026-07-07 反转：用户要求删除一律先 confirm，优先「统一可预期的停顿」而非「高频免打扰」，故单条也弹 simple confirm）。
- 打字确认打固定词「删除」（好打但防误弱，否决，改打实体名）。
- 级联删除「先写库 + 事后 10 秒 undoToast」（与前端已有的打字 + 3 秒实时撤销叠成三重保险，冗余；且整串恢复需记快照，否决，改预提交挂起）。
- 逐条软删除子记录（跨模块关联量大，写入成本高，否决，改父级过滤）。

**后果**：

- 删除一律先 confirm 确认；单条 / 批量再叠事后 10 秒 undoToast（confirm 防「动手前删错对象」、undo 防「手滑后反悔」，两者防不同的错）。级联因前端已有「打实体名 + 3 秒预提交挂起」的高摩擦，不再另给事后 undoToast——「更大的级联反而无事后 undo」是刻意设计，非遗漏。
- 后台所有列表查询必须带「祖先未删」过滤，不能只查自身删除标记。
- 确认弹窗配色：确认按钮 `--danger`、取消 ghost 灰，品牌蓝不当主角；遮罩 `rgba(0,0,0,.28)` 中性轻遮罩（2026-07-05 由品牌蓝改中性黑，避免遮罩抢戏）、不上毛玻璃；Esc / 遮罩点击 / 焦点锁定，打开焦点默认落在「取消」。
- 撤回时长由 5 秒改为 10 秒（见 CONTEXT.md「撤回」词条）。

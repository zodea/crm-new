## 已确认问题

优先级：P1 为可能丢数据、写错对象、混入错误事实或阻断业务；P2 为计算精度及操作偏差。以下业务缺陷尚未在本轮修复。

| 编号 | 优先级 | 问题 | 复现入口 |
| --- | --- | --- | --- |
| A01 | P1 | 固定样例被当作正式项目、客户、分供方返回 | `/project`、`/base/customer`、`/base/supplier` |
| A02 | P1 | 分包合同可用演示身份保存为正式记录 | `/contract/subcontract/form` |
| A03 | P1 | 核心迁移确认后，主档普通读写未接通 | `/settings/data-migration`，随后进入主档列表及项目编辑 |
| A04 | P1 | 多合同编辑页共享写入目标，A 内容发给 B | `/contract/construction/form/:id`；材采、分包表单同型 |
| A05 | P1 | 关闭未保存表单后点取消仍丢输入 | `/base/customer/form` → 页签关闭 → 取消 |
| A06 | P1 | 改成已有票号后仍可重复归档 | `/finance/invoice`、`/finance/invoice/:id` |

### A01：正式来源混入样例

- 条件：全新服务进程、无测试会话头、无 reset、无迁移、`includeDemo=false`。
- 实际：项目返回 `project-real-320`，金额 `5200000.00`；客户返回 `customer-real-320`；分供方返回 `supplier-real-327`，均标 `dataOrigin=real`。
- 定位：`server/utils/project-read-test-instance.ts:301`、`customer-read-test-instance.ts:327`、`supplier-read-test-instance.ts:281` 无条件拼接夹具。
- 验证：直接执行实际 singleton，并由正式空库浏览器失败交叉印证。修复应隔离夹具注入条件，不能把测试断言改为允许假正式数据。

### A02：演示身份进入正式分包合同

- 关闭测试数据，打开分包合同新增页。候选 API 仍提供 12 个演示项目、10 个演示分供方。
- 独立内存进程使用 `proj_demo_001`、`sup_demo_001` 填齐合同字段提交，得到版本 `1` 的正式合同。
- 定位：`server/utils/subcontract-contract-command-test-instance.ts:393`、`server/api/read/subcontract-contracts/form-context.get.ts:13`；校验只判断 ID 是否属于混合候选集合。
- 测试遗漏：`e2e/issue-321-subcontract-contract-detail.spec.ts:58` 把演示候选当作正式新建成功路径。应先建立真实主档，再验证合同保存，另断言演示 ID 被拒绝。

### A03：迁移成功后无法继续使用

1. 用虚构但完整关联的客户、分供方、班组、项目、工人、项目分供方六类资料完成预检、dry-run、导入、确认。
2. 确认结果为 `confirmed`，中央快照含六类实体。
3. 班组、工人普通列表均为零；项目列表能看到迁入项目，进入其编辑页却返回“正式项目不存在”。

定位：`server/utils/core-migration-test-instance.ts:1061` 仅同步三类合同/单据命令源；项目/客户表单查询各自命令 Map，班组/工人读面未消费迁入快照。直接执行完整迁移链已复现。历史迁移 E2E 确认后主要核对项目列表，未覆盖各主档详情与编辑。

### A04：多表单写错目标

1. 打开合同 A 编辑页，再打开合同 B 编辑页。
2. 切回 A，修改名称并保存。
3. 实际 store 向 Repository 发送 `{ id: B, baseVersion: B的版本, draft: { id: B, name: A的新名称 } }`。

定位：`app/stores/construction-contract-command.ts:40`、`material-contract-command.ts:44`、`subcontract-contract-command.ts:36`。单例 `targetId/baseVersion` 被最后一次加载覆盖。已执行真实 store 并捕获错误命令；未向真实后台写入。需按表单会话隔离身份、版本与幂等键，并复用命令机制，不能靠改页签标题解决。

### A05：取消关闭仍丢输入

1. 在 `/base/customer/form` 输入虚构客户名称。
2. 点击该页签关闭按钮。
3. “放弃修改”弹窗中选择取消。
4. 路由仍在表单，但名称为空。

真实浏览器已复现。`app/components/layout/AppTabBar.vue:75` 先删除页签并失效缓存，再执行离开守卫；`MasterDataFormPage.vue:689` 只能补回页签，恢复不了已卸载的输入。后台表单关闭、批量关闭及刷新也需统一经过草稿边界。

### A06：同号发票重复归档

1. 准备两张正常状态的虚构发票，各 113 元。
2. 把第二张票号改为第一张的票号。
3. 分别校对、归档到个人开支。
4. 两次均返回成功；同号台账出现两行，合计 226 元。

真实内存数据库与 store 已复现。`app/stores/invoice.ts:446` 修改票号没有重算重复状态；`:635` 归档门禁仅信任旧状态，未在事务中查同号有效记录。相关发票中央化任务不能代替修复现有防重规则。

### A07：重识别结果被旧表单覆盖

- 打开未归档发票编辑页，重新识别，完成后保存。
- 实际页面脚本与 store 实验：新识别记录为 `OCR-NEW / 226`，本地表单仍为 `OCR-OLD / 113`；保存后数据库退回旧值。
- 定位：`app/pages/finance/invoice/[id].vue:76` 监听已废弃的 `processing → done` 持久化状态；当前流程只使用 `recognitionProgress`。`:166` 保存再次覆写旧表单。
- 验证界限：真实页面脚本和存储路径已运行，OCR 响应使用虚构夹具；未调用真实 OCR。

### A08：工资折算精度

- 日薪 480 元、正常考勤 7.5 小时，应付 `480 × 7.5 ÷ 8 = 450.00` 元。
- 实际先将天数舍入为 `0.94`，得到 `451.20` 元。
- 定位：`app/lib/payroll/statements.ts:1429`。真实考勤写入、草稿生成及读回已复现；应保留计算数量精度，仅在最终金额处按分舍入。

### A09：客户页签标题串改

- 从客户列表打开客户 A，切回列表，再打开客户 B。
- 真实浏览器中两个不同客户 ID 的页签均变成 B 的名称。
- 定位：`app/components/master-data/CustomerDetailScreen.vue:29` 与 `app/stores/customer-read.ts:47` 共用单例详情状态；后台实例的标题监听仍执行。
- 已证实标题污染；未据此推断详情正文或数据写入一定串错。

### A10：保存并新建无效

- 三类合同表单点击“保存并新建”。勾选保存后关闭时进入刚保存记录详情；未勾选时进入刚保存记录编辑页。均未进入空白新建页。
- 定位：`app/components/contract/ConstructionContractFormPage.vue:127`，材采与分包同型处理函数。
- 已执行源码中原始保存函数的两种分支；应将保存并新建与普通保存分开处理。

## 内存与复用

本轮已修复三处无效资源保留：发票文件使用 `useSessionFileCache`，离开工作集后保留 10 秒撤回窗口，到期释放；页签完成卸载后删除历史版本键；送货单重复对照复用 VueUse `useObjectUrl`，忽略过期请求并随页面释放预览。原文件缓存只使用一个 VueUse 计时器，停止作用域时全部清空。复现测试先失败后通过，短时撤回仍能继续识别；四组定向测试共 18 条通过。

修复提交：`a3306cdf`。提交前检查再次通过 376 个测试文件、2,140 条测试。

- 修复前：发票原文件 Map 在删除后仍强引用文件。真实 store 连续上传、删除 20 个 1 MiB 文件后，列表为空，Map 仍持有 20 MiB 逻辑文件负载。修复后，缓存单测到期释放全部文件、计时器归零；真实 Chromium 中以 WeakRef 观察这 20 个文件，主动垃圾回收后，撤回窗口内仍有 20 个存活，窗口结束后为 0。这里记录对象可回收性，不是总堆大小或长期压力测试结果。
- 修复前：页签 `cacheVersions` 在关闭、完成缓存卸载后不删除旧路径；持续打开不同详情再关闭会积累历史键。修复后，连续打开关闭 100 条不同路径均清除版本，卸载完成前快速重开的页签仍保留新实例身份。
- 修复前：送货单重复对照的两个异步请求乱序返回，后返回结果覆盖预览及 URL 清理列表，10 轮并发切换后关闭仍遗留 20 个地址。修复后，真实浏览器 10 轮切换始终显示最后选择，最多保留当前两份预览；关闭页面后及退出后延迟响应返回时，地址均为 0。组件回归还覆盖清空重复队列和旧请求误结束加载。
- 浏览器复验：上述送货单页面在 390 / 768 / 1024 / 1440px 无页面级横向溢出，选择控件可见且可聚焦；页签关闭再打开正常，历史版本清零，无未捕获页面异常。数据与异步延迟均在独立测试会话中构造，未调用外部 OCR。
- 已有复用：`app/components/ui/`、`shared/`、`createSoftDeleteActions`、表单底栏、数据库队列、页签 wrapper。KeepAlive 已限 16 个实例，wrapper 和滚动位置已有释放，不能把这些有界缓存一律判为泄漏。
- 优先复用点：三类合同命令会话、表单关闭确认、请求状态转换及临时文件生命周期。保留各域校验、金额口径与专属详情，避免用通用组件掩盖不同业务规则。
- 当前中央服务是可重置内存证明实例，持久化后台尚未接入；其命令/会话 Map 的长期容量仍需在后台实现时设计，不能随意淘汰幂等记录以换取内存下降。

## Problem Statement

作为工程财务/乙供材管理员，我需要把纸质**送货单**从扫描件走到“归档即形成材料数据供单价对比”，并在打印成功或明确排除前保留原件待办：

- 移植第一波（#47）把送货单列为 Out of Scope、排在倒数第二波；新app 里 `app/stores/delivery.ts` 是**纯 mock**、**无数据库表**、**无识别逻辑**，`material/delivery.vue` 只有 UI 骨架。
- 我手上其实已有一套跑通的送货单识别实现（`invoice-recognition-app`：整理树/分区/云VL识别/明细行结构化/识别明细库入库/单价对比），但它停在旧技术栈、且"更新太多版后界面变差"。
- 我需要把送货单识别**提前**成一个近期独立批次，把现成能力**优化后**移植进 新app 识别中心，落 SQLite、刷新不丢，并按业界优秀产品的排版布局打磨得连贯专业。

## Solution

在 新app 识别中心新增**送货单识别**单页工作台（与发票识别分开、独立页面），把 `invoice-recognition-app` 的送货单六阶段能力移植进来并对齐 新app 架构：

1. **六阶段闭环**：上传→整理树（文件夹层级推断 工地→公司 归属）→分区→识别（统一识别接口，桩/真引擎见 ADR-0006）→人工校对（左图右表明细行）→**归档即入库**（写 `delivery_records` / `delivery_lines` 供单价对比）→打印处置（待打印 / 已打印 / 已排除）。
2. **核心逻辑直接移植**：`delivery-parse`（明细行抽取）、`vl-parse`（一个 PDF 拆多单）、`delivery-tree`（整理树）、`recognized-store`（入库差异合并）、`price-compare`（单价对比）都是纯函数，lift 进 `app/lib/recognize/`，落 SQLite。
3. **数据落 SQLite**：新建 `delivery_records` 表（自然键=工地+公司+单号，唯一索引），单价对比读同一张表，闭环。分供方走 新app `suppliers` 共享主数据（跨项目共享，不重名两套档案）。
4. **UX 对齐业界优秀产品**（见 UX 基准）：常驻六阶段步骤指示器、点明细行↔高亮原图边界框、明细行类 Excel 逐格编辑 + Magic Grid 原图拖线兜底、逐行置信色阶、业务勾稽（数量×单价=金额不平标红）、公司来源三层优先级徽章。
5. **对齐 CONTEXT.md 术语**：送货单归档即入库；送货单必须归项目；识别是动作、台账/归档库是资产；打印成功必须有显式回执。

## User Stories

### 阶段一 · 上传
1. 作为乙供材管理员，我想拖拽/点选文件/选文件夹上传送货单（PDF/PNG/JPG/BMP/WebP/GIF/TIFF），这样各种来源的扫描件都能进流程。
2. 作为乙供材管理员，我想上传含文件夹层级的一批工地资料时自动进入整理树、散文件时直接进列表，这样系统按我的组织方式分流。
3. 作为乙供材管理员，我想上传后文件原地显示"识别中 N%"，这样我知道进度。

### 阶段二 · 整理树（文件夹上传时）
4. 作为乙供材管理员，我想系统按文件夹名推断 工地→公司 的归属并匹配分供方库自动回填公司全称，这样不用手工归类。
5. 作为乙供材管理员，我想在整理树里拖拽移动文件/组、把组升降级为工地，这样能修正自动推断的错误。
6. 作为乙供材管理员，我想纯数字或"未签合同/收据/凭证/杂项"等特殊文件夹被识别为中转组（公司留空待以红章为准），这样杂项不会被错当成公司。
7. 作为乙供材管理员，我想特殊组/待分组里的文件若文件名含某供应商核心名被标"疑似→该组"（仅提示不自动移），这样我有据可依地手动归位。
8. 作为乙供材管理员，我想确认导入后系统创建分区+分配文件+预填公司名，也能从已导入数据"重新整理"重建树，这样整理可反复。

### 阶段三 · 分区
9. 作为乙供材管理员，我想按工地分区切换查看，并能新增/重命名/删除分区，这样按工地组织送货单。
10. 作为乙供材管理员，我想"全部/各工地"分区一键切换，这样在多工地间对照。

### 阶段四 · 识别
11. 作为乙供材管理员，我想点"识别全部"或单张识别，走统一识别接口出 公司名/日期/单号/材料明细行，这样机器先干一遍。
12. 作为乙供材管理员，我想识别失败时自动旋转 90°/270° 重试（横躺扫描件），这样常见的方向问题自动解决。
13. 作为乙供材管理员，我想一个扫描 PDF 含多张单时自动按表格拆成多张单，这样合并扫描也能逐单处理。
14. 作为乙供材管理员，我想未配置云识别（若走云）时被拦截门提示去配置或确认仍用本地，且"仍用本地"能记住不再反复问，这样不被打断。

### 阶段五 · 校对（重点，吸收竞品 UX）
15. 作为乙供材管理员，我想在文件卡片上左看原图缩略（悬停放大镜）、右改明细行，同屏就地校对不跳页，这样校对顺手。
16. 作为乙供材管理员，我想点某明细行时左侧原图对应区域高亮边界框（双向联动），这样快速核对每行抠得对不对。
17. 作为乙供材管理员，我想明细行像 Excel 一样逐格编辑（点选即改、Tab/Enter 跳格、复制粘贴、行首增删行），这样录入高效。
18. 作为乙供材管理员，我想数量×单价自动补金额、我手改金额后不再被覆盖，这样常规行零手工、特殊行可保留。
19. 作为乙供材管理员，我想数量×单价≠金额的行被当场标红并定位，这样算术错误不漏到下游。
20. 作为乙供材管理员，我想低置信的行/格标黄、并能"只看未完善"筛选（缺公司/缺日期/缺单号/0明细行/待复核），这样精力集中在可疑处而非逐行全查。
21. 作为乙供材管理员，我想引擎切错行列/漏识别整行时，在放大的原图上拖表格网格线并把列绑到 名称/单位/数量/单价/金额，一键重转录该表，这样版式杂的单据有救济。
22. 作为乙供材管理员，我想公司名来源（文件夹/OCR/手动）以徽章标明、冲突时二选一亮牌，这样知道公司名从哪来、按红章定夺。
23. 作为乙供材管理员，我想手动覆盖公司名/日期/单号/增删明细行/移动分区，这样人工始终能纠正机器。
24. 作为乙供材管理员，我想识别失败/无法读取/公司冲突/部分识别集中到一个问题汇总弹窗，这样批量收口异常。

### 阶段六 · 归档与打印处置
25. 作为乙供材管理员，我想把校对定稿的送货单归档到材料台账（自然键=项目+分供方+单号），归档明细立即供分供方详情/单价对比读取。
26. 作为乙供材管理员，我想归档时对已存在的同键记录做差异合并（全新写入、完全相同跳过、有冲突人工确认），避免重复归档扰乱材料数据。
27. 作为乙供材管理员，我想缺项目或缺关键自然键的单被扣下单列等补、不归档，保证材料台账完整性。
28. 作为乙供材管理员，我想新归档原件默认保留在待打印范围，打印机实际输出成功后再确认回执并移出队列。
29. 作为乙供材管理员，我想可以明确把某原件排除打印；排除只记 `excluded`，不能显示为已打印。

### 单价对比（归档下游闭环）
30. 作为乙供材管理员，我想单价对比页读 `delivery_records`（+ 可选历史 Excel），把规格归一化后精确归组，行=材料列=供应商展示最近价/区间/最低价，这样跨供应商比价一目了然。
31. 作为乙供材管理员，我想运费/搬运/管理费等非材料项默认从比价里剔除（可学习留痕），这样比价只比材料。
32. 作为乙供材管理员，我想对归组过粗/过细的材料手动并组，这样比价分组贴合我的真实口径。

### 归属与主数据
33. 作为乙供材管理员，我想送货单归属绑定到 新app `project`（送货单必须归项目），这样材料成本能落到具体项目。
34. 作为乙供材管理员，我想公司名匹配走 新app `suppliers` 共享主数据（全称/别名/核心名），这样不会出现重名两套档案。

### 持久化与质量
35. 作为乙供材管理员，我想我的送货单数据落 SQLite、刷新/重启不丢，这样这是真工具。
36. 作为开发者，我想明细行抽取/整理树/入库差异合并/单价对比归组的纯逻辑有 vitest 回归（沿用源项目离线回归先例），这样移植不走样。
37. 作为乙供材管理员，我想送货单识别与发票识别复用同一套校对组件（边界框高亮/置信度输入框/明细网格/问题弹窗/底部操作条），这样两界面交互一致、学一次通用。

## Implementation Decisions

- **独立页面**：送货单识别与发票识别**分开**（不共用工作台，只共用底层原语：上传区/统一识别接口/左图右X 布局/置信度着色/BoundingBoxOverlay/明细网格）。路由沿用 `/material/delivery`，~~侧边栏归入**识别中心**菜单组~~（⛔ 识别中心组已退役 2026-07-09：送货单识别归**乙供材管理**组，现行导航结构以设计稿 NAV 锁定版为准——ADR 0013 / CONTEXT.md「识别中心」词条）。
- **纯逻辑层移植**（`app/lib/recognize/`，lift-as-is/with-adapt，JS→TS + 单测同搬）：`delivery-parse.ts`(源 parse.js)、`vl-parse.ts`、`delivery-tree.ts`、`supplier-match.ts`(源 supplier-db.js 的匹配/归一化纯函数)、`recognized-store.ts`(classifyUpsert/recordsEqual/docToRecord)、`price-compare.ts`。详见移植方案 §2/§8。
- **表 `delivery_records`**：归档头与打印处置；`delivery_lines` 保存材料明细。归档动作同时形成单据资产和材料台账资格；`print_disposition` 只表达打印后续，不参与单价分析资格判断。
- **分区/整理树落 delivery store**：`app/stores/delivery.ts` 从 mock 换真数据，补 staging(整理树)/partition(分区)/requestOcr/降级 actions；`matchSupplier` 数据源改查 `suppliers` 表（含 alias，若无则补一列或 JSON）。
- **统一识别接口**：`app/lib/recognize/engine.ts` 封装引擎，对上暴露 `recognize(docType, pages) → { markdownPages, layoutRegions?, engine }`。引擎已定为 **PaddleOCR-VL-1.6 单模型（本地自托管为主，MLX-VLM/llama.cpp）**（ADR-0006）：一个模型出 OCR+表格+手写+版面 Markdown，送货单明细行由 `vl-parse.js` 在 Markdown 上抽取；本地走 localhost 无 CORS，云端 aistudio 仅开发期脱敏用。
- **OCR 设置页 + 拦截门**：`app/stores/ocr-settings.ts`（token 留 localStorage 不进库/不进代码/不进 git）+ 蓝本形态设置页 + KitUI confirm 拦截门（记住 ack）。
- **归属**：送货单必须归 `project`；工地名→project 绑定 = **别名表归一**（前置决策3 已定：`project_aliases` 命中自动绑、未命中模糊候选+人工确认后写回；自然键全 ID 化，原文本仅留痕）。
- **UX 增补**（对齐 UX 基准，均为蓝本上做加法）：常驻六阶段步骤指示器；`BoundingBoxOverlay` 组件（点明细行↔高亮原图，依赖引擎返回坐标，缺坐标降级不高亮不报错）；明细行类 Excel 逐格编辑 + Magic Grid 原图拖线兜底；逐行置信色阶（黄/绿/红/灰统一色卡贯穿列表点/原图框/输入框/明细行底色）；业务勾稽（数量×单价=金额不平标红）；公司来源徽章 + 冲突二选一。
- **不搬**：`@paddleocr/api-sdk`（未用）、isTauri/tauriInvoke 桌面分支、vite proxy/中间件、recognized-io 双通道、app-settings localStorage 实现、reka-ui、Precision Ledger 重壳（侧边栏+多阶段状态机+独立编辑路由，"变差"病灶）。详见移植方案 §10。
- **依赖底座**：纯逻辑层可先做；识别 UI 组件（FileCard/FieldsTable/DeliveryTree）依赖 KitTable/KitAtoms/页签/软删——**UI 层必须等核心底座就位**（CONTEXT.md 顺序：KitUI原语→核心底座→识别域）。

## Testing Decisions

- **好测试的标准**：只断言外部行为——纯函数的输入→输出、数据库可见状态、页面可见文本/元素；不断言内部实现。
- **vitest（纯逻辑层，最高优先、可先做）**：
  - `delivery-parse`：给定 OCR 文本行 → 抽出的 date/orderNo/company/items 正确（含续行合并、单位识别、服务类项、autoTotal）。
  - `vl-parse`：给定 VL Markdown（HTML table）→ 拆出的多张单与明细行正确（表头列映射、合计行过滤、行级算术校验）。
  - `delivery-tree`：给定文件夹层级 → 工地/组/文件归属、同名合并、特殊组中转、疑似建议正确。
  - `supplier-match`：全称/别名/核心名匹配优先级正确。
  - `recognized-store`：classifyUpsert 分 inserted/identical/conflicts 正确、缺键 heldBack、recordsEqual 逐行比对。
  - `price-compare`：规格归一化归组、每供应商最近价、lowest、运费剔除、obs 去重正确。
  - **先例**：源项目 `scripts/selftest.mjs` / `test-invoices.mjs` 的离线回归可直接移植为 vitest 用例。
- **数据层接缝（SQLite）**：`delivery_records` 的 upsert（自然键唯一、冲突保留旧值/勾选覆盖）、单价对比读回同表；走 `connection.ts` 的 execute/select + sql.js 内存库测。
- **Playwright E2E（等 UI 就位）**：送货单主干旅程——上传文件夹→整理树归属→分区→识别（桩/真）→校对→归档并由单价对比读回→待打印→打印回执或排除；只覆盖主干不逐像素。
- **视觉验收**：与蓝本 + UX 基准逐屏人工对照。

## Out of Scope

- **PaddleOCR-VL 本地部署的一次性搭建**（装 MLX-VLM/llama.cpp + 下 1.6 权重 + 暴露本地 server）：属基础设施，单独落地；本 PRD 只约定"走统一识别接口 + `ocr-vl.js` 指向该端点"。引擎决策见 ADR-0006。
- **发票识别**（独立 PRD/批次，见 #47 及发票域移植）。
- **清单拆表 / 工程量 / 工人工资**（后续批次）。
- **Tauri 打包与桌面端 Rust OCR 代理、真实文件系统落盘**（归档导出到"生成整理包"为止，浏览器内模拟+下载降级）。
- **证照 OCR 旁路**（credential-ocr，配 supplier_credentials，收尾增量）。

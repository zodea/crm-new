# 送货单识别 — 上传·识别·归档·打印

> 路由: `/material/delivery`
> 页面: `pages/material/delivery/index.vue` → `components/delivery/DeliveryRecognitionScreen.vue`
> 来源: 现有 DeliveryView + delivery store 代码分析；2026-07-17 已接入真实 OCR 闭环
> 真实票据 Excel 结构、合并单元格和导入导出兼容规则见 [`real-ticket-excel-reference.md`](./real-ticket-excel-reference.md)。

> **现行 IA：处理区与归档库双区。** 权威见 `CONTEXT.md`「归档」词条、[#42](https://github.com/zodea/crm-new/issues/42) 与 [#113](https://github.com/zodea/crm-new/issues/113)：
> - **处理区 = 送货单识别**（乙供材管理 · route `delivery`，本页下文的上传/整理树/识别/核对流程）：放**待识别 / 识别中 / 待核对 / 待打印**；归档后原件仍留在待打印范围，直到收到打印成功回执或被明确排除。
> - **归档库 = 送货单归档库**（乙供材管理 · route `deliveryArchive`，设计稿 `kit/DeliveryArchiveScreen.jsx`）：已归档件的**左树右列表**。左树两级 **项目 → 分供方**（分供方按其合同**签订日期升序**），每项目下设 ⚠**「未区分分供方」**兜底节点；**所有节点带文件数量角标（只数量不金额）**；点树节点出该节点文件列表。
> - **归档规则**：核对是归档前置但不等于自动归档；归属信息齐全并由用户触发归档后才进入归档库。未指定项目**禁止归档**（批量/单个同拦截）。
> - **归档即入库**：送货单归档时单头、材料明细和原件一并持久化；`archived=1` 是材料事实的读取资格，不另设第二个“入库”按钮或状态。单价分析仍只读取人工确认后的有效单价；“价格待补录”行在补录前不进入分析。
> - **打印独立处置**：新归档默认待打印。“打开打印”只打开原件/系统打印窗口，不改变状态；打印机实际输出后由用户另点“登记已打印”才移出队列，手动排除只记已排除。同一上传文件即使识别出多张送货单，也按持久化打印批次恢复为一个任务。
> - **归档不是终态**：单条归档记录可从详情或整页编辑入口改归属/字段，任何修改一律弹**二次确认**（识别难免出错，留改错通道）。文件拖拽批量改归属、批量归属调整和手动新建归档节点暂不属于当前实现，后续另立工作项。
> - **分供方名模糊纠错**：识别/文件夹推断的公司名在分供方库模糊匹配 → 只给建议，必须人工采用后才绑定；确认的 OCR 写法记入分供方别名。
> - 下文阶段一至三的“文件夹整理树 / 分区 / 上传时归属拦截”是**未落地历史目标**，不是当前运行行为。当前先上传识别，在核对归档前强制选择项目；若恢复“上传时拦截”，须作为独立工作项同时调整交互和会话模型，不能只改文案。

> **实现差距（2026-08-11 核对）**：处理区已经打通上传、裁边扶正、OCR、表格解析、三栏核对、归档即入库和跨刷新待打印队列；打印采用“打开原件 → 用户完成系统打印 → 明确回执”的保守闭环。归档库已经可以按当前筛选导出固定结构 ZIP：Excel 明细、原始 PDF/图片、缺失留痕，以及用户可选的只含图片的合并 PDF。文件夹整理树、批量改归属、可配置导出目录，以及多份 PDF 保持原对象的无损合并仍属后续工作。OCR 模型、隐私边界、Token 与预处理策略只以 [ADR-0006](../../adr/0006-ocr-paddleocr-vl-single-model.md) 为准；原件保真边界以 [ADR-0019](../../adr/0019-delivery-export-source-preservation.md) 为准。

> **#253 人工校对边界（2026-08-07 已收口）**：所有 OCR 结果先生成“待人工归档”草稿，不因置信度或版式标准而自动归档。标准版式可自动预处理；手写、低清、字段不足或非标准单据进入人工处理队列。缺单价或金额时，经人工查看原件并确认送货事实后可先归档，但必须标记“价格待补录”，且在补录并确认有效单价前不得进入价格分析；数量×单价与金额不一致时标记“金额待复核”，人工确认并填写原因后才能归档。供应商或日期缺失不得自动补全；单号缺失可在人工确认后归档并标记“原件无单号”。每行材料名称、单位和非零数量必须人工确认；相同文件只识别一次。

> **2026-08-13 运行态补验**：参考站当前菜单没有可安全确认的一一对应“送货单识别/归档库/材料价格”页面，因此这些瑞航独有工具继续以本地 DC 与本规格为视觉和业务权威，不从相邻页面外推上传、OCR、归档、下载或导出行为。相邻的材料到货列表可见“源单据、送货单编号、合同、分供方、仓库、结算/付款状态”，材采合同详情的“物资管理”又按新/历史入库、直入直出、新/历史出库聚合，证明送货归档必须成为到货链的可追溯来源，而不是另一套孤立台账。完整只读证据见 [`material-management.md`](./material-management.md) 与 [运行态参考审计](../../design/runtime-reference-audit.md)。

### 当前数据与状态词汇缺口

- 本地初始库有 3 个 `archived=1` 送货单头和 4 条材料明细；2 个头已绑定分供方并含有效单价，另 1 个进入“未区分分供方”。三条记录都没有持久化原件正文，详情正确显示“缺原件/补传原件”状态。
- 归档库列表、送货单号详情、项目详情、分供方详情，以及单价分析中的来源送货单/历史材采合同下钻均已存在；列表返回详情后仍需恢复原项目—分供方树节点、搜索、日期和分页上下文。
- `delivery_records.ocr_status` 当前持久化人工核对完成态为 `reviewed`，`buildMaterialPriceCatalog()` 却在收到 `ocrStatus` 时只接受 `done`。因此运行态 `/material/price` 会把上述已有价格事实全部过滤并显示“尚无可分析的材料价格”。修复必须统一“识别完成”和“人工核对完成”两个状态维度，兼容存量 `reviewed`，不得通过补 Mock 数据绕过。
- `delivery_records` 与 `material_arrivals` 目前没有 canonical 外键或分配桥表；送货单号相同、材料名相似或金额相等都不能作为数据库关联。数据迁移前须先裁定一张原件拆多张送货单、一个送货单分多次入库时的基数，再选择单 FK 或显式分配表。

## 一、交互流程（历史六阶段目标）

> ⛔ 本节阶段一至三保留作文件夹整理后续设计输入；当前页面没有文件夹整理树或分区栏。现行状态以文首“实现差距”和下方阶段四至六说明为准。

### 阶段一 · 上传入口

```
UploadZone
  ├─ 拖拽 / 点击选文件 / 选文件夹
  ├─ 支持 PDF、PNG、JPG、BMP、WebP、GIF、TIFF
  │
  ├─ 有文件夹层级? → 进入整理树 (stageEntries)
  └─ 散文件? → 直接加入列表 (addFiles)
```

### 阶段二 · 整理树（仅文件夹上传时出现）

```
DeliveryTree
  ├─ 按文件夹名推断 工地→公司 归属
  ├─ 匹配分供方库自动识别公司名
  ├─ 拖拽：文件移组、组移工地
  ├─ 升/降级：分组 ↔ 工地互转
  │
  ├─ 确认导入 → applyStaging()：创建分区+分配文件+预填公司名
  └─ 取消 → discardStaging()
```

"重新整理"按钮可从已导入的 store 数据重建整理树（`stageFromStore()`）。

### 阶段三 · 文件列表 + 分区

```
PartitionBar: 全部 / 各工地分区切换 + 新增/重命名/删除
FileCard × N:
  左栏: 预览缩略图 + 状态 chip
  右栏: 公司名、日期、单号、明细行
  操作: 移动分区 / 识别 / 删除
```

### 阶段四 · OCR 识别

```
触发: "识别全部" 或 单张识别
  └─ 调用统一 recognizeDocument(file) 接口
      ├─ 图片与可解析的单页 PDF 可生成裁边扶正 PNG 派生件；多页/解析失败 PDF 保持原文件
      ├─ 输出 Markdown / HTML 表格 / layout regions
      └─ 失败显式报错并允许会话内重试

结果写入:
  ├─ 公司名（检测冲突：文件夹名 vs OCR）
  ├─ 日期、单号、明细行
  ├─ 单据类型：送货单 or 收据
  └─ 状态: done / error / ocrPartial
```

### 阶段五 · 人工校对 + 问题处理

```
FileCard 内编辑:
  修改公司名(手动覆盖) / 日期 / 单号 / 增删明细行 / 移动分区

ProblemDialog:
  识别失败→重试 / 无法读取→手动录入 / 公司冲突→三选一 / 部分识别→核对

"只看未完善" 筛选:
  缺公司 / 缺日期 / 缺单号 / 0明细行 / 待复核
```

### 阶段六 · 核对、归档与打印

归属齐全并由用户触发归档后，单据进入归档库；有人工确认有效单价的材料行同时获得单价分析资格，“价格待补录”行除外。不再有独立入库动作。打印仍是归档后的单独状态机。

| 路径 | 当前行为 |
|------|------|
| 核对并归档 | 强制选择项目；把人工确认后的单头、材料明细和原件写入 `delivery_records` / `delivery_lines` / `file_refs`，归档即入库 |
| 分供方未命中 | 允许归到项目下“未区分分供方”，保留 OCR 供应商原文供后续纠正 |
| 待打印 | 归档后默认保留在打印工作队列；同一上传文件的多张识别单共享 `print_batch_id`，跨刷新仍恢复为一个任务 |
| 打开打印 | 只打开原件和系统打印窗口，不写打印状态；取消、失败或关闭窗口都继续保留 |
| 登记已打印 | 打印机实际输出后由用户单独确认；整批记录都仍为 `pending` 才原子写 `printed` 并移出队列 |
| 排除打印 | 用户明确不打印时写 `excluded` 并移出待打印范围；`printedAt` 保持为空 |

## 二、归档手工新增与编辑

`deliveryArchiveForm` 是归档库统一的整页表单入口：`/material/delivery/archive/form` 手工新增，`/material/delivery/archive/form/:id` 编辑既有记录。列表的“新增送货单”和行内“编辑”、详情页“编辑”都导航到该整页路由，不再打开大型弹窗。编辑既有归档时保存前使用二次确认；手工新增保存后即归档并进入材料台账。

| 分区 | 字段与规则 |
|---|---|
| 档案信息 | 仅编辑既有记录时显示文件名、OCR 识别公司与原件只读留痕 |
| 归属 | 项目*、分供方（可空=未区分分供方），均为真实 lookup |
| 单据字段 | 送货单号、送货日期、材料摘要、单据金额 |
| 备注 | 备注 |

改项目/分供方后重新校验去重自然键；材料摘要和单据金额保存人工核对结果，材料行仍是入库与单价对比的明细事实。

## 四、归档库原件包导出

归档库当前工具栏按页面筛选结果直接生成 ZIP，不进入 ADR 0004 的可配置目录页签。包内包含：

- `送货单明细.xlsx`：按材料明细行展开，并记录缺原件、共用原件、未区分分供方和价格缺失等异常。
- `导出说明.txt`：说明本次保真范围、图片转换结果和缺原件记录。
- `原件/PDF/`：每份 PDF 原件以原始字节整份保留；多页不拆分，共用源只入包一次。
- `原件/图片/`：图片保持原格式。用户勾选“图片另生成 PDF”且存在可转换的 PNG/JPG 时，包内另有只含图片的 `图片原件合并.pdf`。

当前不把 PDF 原件加入图片合并件，也不通过 Canvas/JPEG 重建 PDF。多份 PDF 真正保持原对象与页面结构的合并仍待后续依赖选型与实现；当前能力不得表述为“所有原件已合并 PDF”。

## 六、未完善检测规则

```ts
function fileIncompleteReasons(f: DeliveryFile): string[] {
  // 识别失败 / 无法读取 / 公司冲突未解决 / 部分识别
  // 公司为空 / 日期为空 / 单号为空(送货单) / 0明细行 / 待复核
  // 收据模式: 检测材料名称/单位/单价是否为空
}
```

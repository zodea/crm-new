参考甲方报量详情确认了以下隐藏只读层级：顶部摘要（项目、审定产值、本次结算、奖罚、生效状态）→ `详细资料 / 合同清单 / 变洽签清单 / 扣款与奖励 / 结算转扣记录` → 审批历史/完整流程。详细资料再按基础信息、甲方审定结果、前期累计、合同金额合计与系统信息分段，项目、合同和甲方名称均是关系入口；附件以文件集合呈现。#323 已将甲方变洽签/月度报量收口为中央只读详情，#324 追加验收/保修 canonical 双视图，#325 追加最终结算，#326 追加甲方罚扣专属只读详情；正式编辑统一分流到 `/owner/:kind/form/:id`。只有真实持久化的量价、审批摘要与附件被展示，未闭合的奖罚/完整审批轨迹不伪造。

列表到详情、详情内关系下钻和返回必须携带可恢复的来源上下文。读路由统一接受站内白名单 `returnTo` 或等价结构化来源，并保留原列表的 `project`、`contract`、`supplier`、搜索、类型、状态、视图、页码、滚动和行焦点。#323—#326 已闭合五类甲方单据的全局列表、项目、客户、施工合同和相关来源往返；#327 已闭合分包变洽签与全局列表、项目、分供方、分包合同及合同变洽签事实行的稳定 ID 往返。#283 父级联合验收进一步要求项目详情提供六张甲方单据卡片；#327 只追加一张分包变洽签卡片，均按当前项目稳定 ID 查询同一中央 Repository，并通过受限嵌套 `returnTo` 恢复卡片锚点、滚动和焦点。

Issue #325 的最终结算详情展示结算申报金额、真实审定金额/日期、原合同金额、变更后合同金额、累计收款、结算收款差额、结算依据、差异说明、附件和来源表。变更后合同金额只聚合非草稿补充协议，累计收款只聚合活跃收款；两类来源在独立横向滚动区按稳定 ID 下钻。审定事实未记录时显示“未记录”，不用申报值或零值代替；当前只开放草稿保存与提交，不展示未实现的审定动作。

Issue #326 的甲方罚扣详情独立展示负向罚扣金额、日期、状态、联系单号、事由、申诉说明、备注和联系单附件，并按真实项目、甲方客户、施工合同和罚扣源单下钻。列表编号与施工合同“验收结算”分区中的罚扣事实行都进入同一稳定 ID；返回恢复原列表或合同分区、行与焦点。状态只使用 `draft → submitted`；申诉说明是业务事实，不生成“申诉中/已确认”审批流，也不进入项目罚扣或分包结算抵扣。

Issue #327 的分包变洽签详情独立展示审批金额、变更面积、实际审定价、日期、类型、事由、状态、备注和签证单附件，并按真实项目、分供方、分包合同和源单下钻。全局列表、项目卡片与分包合同“分包变洽签”事实行进入同一稳定 ID；返回恢复原筛选或合同分区、行与焦点。正式草稿或已退回记录才显示显式编辑入口，状态只开放 `draft → submitted`；未实现审批动作不生成假按钮，金额语义不借甲方变更或分包结算补齐。

参考空列表仍完整显示类型导航、专属表头、汇总和分页，因此空数据不能成为合并入口或删列的理由。当前基础 seed 仅有 2 条 `owner_change_orders` 和 1 条 `monthly_statements`；`project_acceptances`、`owner_final_settlements`、`owner_penalties`、`subcontract_change_orders`、`expenditure_settlements`、`penalty_records` 均无基础 seed。实现可以先交付真实空态和读模型，但需要后续用确定性、互相关联的脱敏 seed 覆盖至少一个甲方流程和一个分包结算/罚扣流程，禁止继续用 MockJS 行数据绕过 SQLite。

项目、合同或分供方详情进入列表时，可通过 `project`、`contract`、`supplier` query 预设来源范围。页面必须显示当前来源条件；用户可单独清除来源条件，不能把 query 静默丢弃，也不能因未知 ID 显示一张未筛选的全量表。

每类列表使用自己的业务标题、搜索提示和列：

- 共同骨架为“标题与说明 → 单行搜索/筛选/刷新/新建 → 紧凑表格 → 当前筛选汇总与分页”。
- 共同事实列为编号、项目、状态和进入原类型编辑页的入口；名称/事由、合同/分供方/班组、类型、金额、日期按上表类型显示。
- 金额完整显示并按当前筛选结果汇总。长编号不得截成无法辨认的省略号；超宽表格只在表格区域横向滚动，末尾操作保持可达。
- 无任何记录时显示该类型的“暂无记录”空态和新建入口；搜索或筛选无结果时显示“没有匹配结果”和“清除筛选”；加载失败显示原因和“重新加载”，不能伪装成空数据。
- 搜索、项目、类型、状态或来源范围变化后回到第一页；分页只切换可见结果，不改写业务数据。
- 五类甲方单据与分包变洽签的中央列表把搜索、项目、合同、分供方、类型、状态、页码和每页数按各 kind 交给读 Repository；`items`、`pagination.total`、`summary` 和筛选 facet 均在服务端完整结果上计算，不先取 100 条再在客户端切页。

## 二、整页表单

8 类单据均使用独立路由整页表单：新建为列表路由追加 `/new`；五类中央甲方单据的编辑为 `/owner/:kind/form/:id`，分包变洽签编辑为 `/subcontract/change/form/:id`，分包结算编辑为 `/subcontract/settlement/form/:id`，项目罚扣当前沿用既有表单路由。标题必须是“新建/编辑 · 真实类型名”，返回动作回到经验证的来源详情或原类型列表。

### 甲方变洽签

| 分区 | 字段与规则 |
| --- | --- |
| 基本信息 | 变更编号、变更名称*、项目*、施工合同*、类型、甲方指令单编号、指令类型、申报日期* |
| 金额 | 含税审定金额、无税审定金额、无税申报金额；与量价明细合计展示勾稽 |
| 变更明细 | 分项*、单位、调量差值、调价后单价、变更合价、备注 |
| 事由与流转 | 变更事由*、状态说明 |
| 附件 | 我方指令单、甲方指令单、报价与算量、施工照片 |

量价变更复用 `boq_change_orders` / `boq_change_lines`，不得再建副本；不含量价明细的纯金额签证才直接进入业主变洽签台账。调量允许负差值，但调整后有效合同量不得为负；调价金额按先前已签证调量/调价后的有效量价计算，页面与中央命令共用同一规则。确认签证只写独立签证日期，不覆盖用户填写的申报日期；日期必须是真实日历日，且不得早于同合同既有签证时序尾，同日签证使用签证 action 冻结的单调服务端执行时间续排，不以通用更新时间或单据 ID 决定业务顺序，后续附件维护也不得重排，以保证签证时重算与有效 BOQ 重放使用同一顺序；同时锁定收入变更台账。若存在后续金额链，不能原地篡改，须按 BOQ 更正规则处理。

### 甲方报量

报量编号、项目*、施工合同*、报量期次*、申报日期*、报量经办人、申报产值、审定产值、审定差额只读、报量明细、状态、备注和扫描件。报量明细从月度完成量事实生成，申报时保留快照；人工调整和甲方审定值留痕，不复制另一套完成事实。

申报（提交）时冻结经办人与系统提交时间，草稿期两者留空——用户手填的“申报日期”不能当作系统提交证据。取数时的来源版本与源数据更新时间随生成/重算写入，用于证明已申报单据依据的是哪一版工程量事实。

甲方报量单与 BOQ 工作台的月度报量是 `monthly_statements` 里的同一条记录，因此自动完成量必须读该单据已冻结的 `quantity_basis`（合同量 / 暂估量 / 现场复核量，枚举与列名映射见 `app/lib/quantity/basis.ts`），两侧不得各按各的口径派生；该期次尚无单据时才回落默认的现场复核量。

所选基准缺量的清单行在明细网格标注“缺量”，自动完成量显示为 0 但仍带入明细，不回退到另一口径，也不因自动量为 0 被过滤掉。与 BOQ 工作台“自动生成整单、缺量直接阻断”不同，甲方报量单是人工编辑面：缺量只标注，由用户显式决定申报量。

### 验收、结算与甲方罚扣

| 表单 | 字段与规则 |
| --- | --- |
| 竣工验收·保修 | 共享单据编号、名称*、项目*、施工合同、合同估价和备注；验收视图维护验收单位/人/日期/结论与验收报告，保修视图维护负责人、起止日、到期确认单位/日期/说明与确认单附件 |
| 最终结算 | 结算编号、结算名称*、项目*、施工合同、结算金额*、报审日期*、变更后合同金额/累计收款/结算收款差额只读、结算依据、差异说明、状态、备注、结算书 |
| 甲方罚扣单 | 罚扣编号、项目*、施工合同*、联系单编号、罚扣金额*、日期*、罚扣事由*、申诉说明、状态、备注、联系单扫描件 |

验收和保修是同一记录的连续生命周期；视图切换不改变 acceptance ID，也不从状态反推未记录的日期、结论或历史。最终结算独立保存甲方审定事实，不复用支出结算；甲方罚扣金额不得混入项目罚扣或分包结算抵扣。

### 分包单据与项目罚扣

| 表单 | 字段与规则 |
| --- | --- |
| 分包变洽签 | 变更编号、类型、项目*、分供方*、支出合同*、日期*、审批金额*、变更面积、实际审定价、事由*、状态、备注、签证单 |
| 分包结算 | 结算编号、结算名称*、项目*、分供方*、支出合同*、结算类型、结算金额*、日期*、合同金额/往期结算/占比只读、扣款说明、状态、备注、结算单 |
| 项目罚扣 | 罚扣编号、项目*、分供方、支出合同、班组、日期*、罚扣事由*、罚扣金额*、扣除方式、整改期限、整改说明、状态、备注、罚款照片 |

分包结算复用 `expenditure_settlements`。分包变洽签、分包结算和项目罚扣没有独立业务明细子表，不显示虚构编辑网格。项目罚扣可关联分供方、合同或班组；执行抵扣时必须选择真实、已确认且与来源一致的分包结算，并把抵扣关系写入独立事实，不在罚扣头保存“已扣金额”副本。

## 三、状态与动作

DC 源码提供页面语言；数据库中的英文状态是权威值。界面将同义词映射为中文，不为对齐示例而新增无后端动作的状态。

| 类型 | 本地状态旅程 | 用户动作与约束 |
| --- | --- | --- |
| 甲方变洽签 | 草稿 → 已提交 → 已签证；已退回可编辑后重报 | 上报前校验项目、施工合同、事由及量价明细或纯金额；签证需二次确认并锁定收入变更 |
| 甲方报量 | 草稿 → 已申报 → 已审定 | 申报锁定当期完成量快照；审定逐行保存审定量和金额 |
| 竣工验收·保修 | 草稿 → 已提交 → 已验收 → 保修中 → 保修到期 | 上报、确认验收、开始保修、确认到期均走真实 command；每次追加 actor、发生时间、前后状态和备注，越级/重复推进拒绝，到期终态只读 |
| 最终结算 | 草稿 → 已提交 | 当前本地闭环只承诺提交并保存最终结算事实；“已审定”仅在有真实审定 action 后开放 |
| 甲方罚扣单 | 草稿 → 已提交 | 申诉说明是业务事实，不等同于已经存在申诉审批流 |
| 分包变洽签 | 草稿 → 已提交；已退回可编辑后重报 | 只关联所选项目、分供方下的真实支出合同；未实现的审批动作不显示假按钮 |
| 分包结算 | 草稿 → 已确认 | 确认后进入支出结算事实，并可作为项目罚扣抵扣来源 |
| 项目罚扣 | 草稿 → 待抵扣 → 已抵扣 | 可记录整改信息；执行抵扣必须选择真实结算，部分抵扣继续显示剩余可抵扣金额 |

删除继续服从各实体当前已有的领域保护，不因对标界面新增虚假审批规则。已签证甲方变洽签明确禁止普通删除或改写；其他单据形成受保护下游事实后，也必须由对应领域 action 处理，不能通过界面按钮绕开审计链。

已上报变洽签和已申报月度报量的只读详情仍显示“处理流转”，进入同一整页表单执行签证/审定；草稿才显示编辑。表单保留打开时的 `baseVersion`，保存前不重取最新版本绕过 409；取消、提交、签证和审定后回到经验证的来源详情。

## 四、来源、附件与持久化

| 类型 | 业务头/明细 | 附件 `owner_type` |
| --- | --- | --- |
| 甲方变洽签 | `boq_change_orders` / `boq_change_lines`；纯金额签证兼容业主变更头 | 按实际变更存储实体解析，不建立重复附件 |
| 甲方报量 | `monthly_statements` / `monthly_statement_lines` | `monthly_statement` |
| 竣工验收·保修 | `project_acceptances` + `project_acceptance_lifecycle_events` | `project_acceptance`；附件分类为 `acceptance-report` / `warranty-confirmation` |
| 最终结算 | `owner_final_settlements` | `owner_final_settlement` |
| 甲方罚扣单 | `owner_penalties` | `owner_penalty` |
| 分包变洽签 | `subcontract_change_orders` | `subcontract_change_order` |
| 分包结算 | `expenditure_settlements` | `expenditure_settlement` |
| 项目罚扣 | `penalty_records`；抵扣关系独立保存 | `penalty_record` |

- 项目、合同、分供方和班组 lookup 保存真实 ID，并校验合同确实属于所选项目与业务方向。
- 分供方详情和分包合同事实行只有在服务端返回 `subcontract-document:read` 时生成分包变洽签入口；分供方来源往返用受限上下文恢复入口锚点、滚动与焦点。
- 表单中的来源 lookup 只接受合法真实记录；找不到来源或来源关系冲突时，显示可恢复错误并保留用户已填内容。
- 附件统一写 `file_refs`，分类标签随单据类型呈现；附件失败不得把业务保存伪装成全部成功。
- 只读带出和聚合金额不保存；分包实际审定价汇总保留“完整、部分、缺失”状态，不能把缺失值当作零。申报、审定、申诉、整改和抵扣等具有审计价值的事实按对应实体或操作日志保存。

## 五、响应式、键盘与错误恢复

- 在 390、768、1024 和 1280–1440px 验证列表、新建和编辑；页面本身不得横向滚动。
- 窄屏筛选按“搜索 → 项目 → 类型 → 状态 → 操作”换行，表格仍只在自身区域横向滚动；金额和编号提供完整可读内容。
- 所有筛选、分页、清除来源、新建、行入口、保存和状态动作均可用键盘到达，并显示可见焦点。
- 提交校验失败时在字段旁显示具体错误，设置 `aria-invalid`，并聚焦首个无效字段；明细错误定位到明细网格的可聚焦错误提示。
- 编辑加载失败显示错误与“重新加载/返回列表”；不得把失败页渲染成一个可覆盖原记录的空白新表单。
- 草稿、已退回、进行中和终态使用一致但可区分的状态标签；空态、加载态、错误态和保存中的禁用态不得混淆。

## 六、验收

1. 8 类列表和 8 类新建/编辑页均显示真实动态标题、专属列/字段/状态，返回原类型且未知 `kind` 为 404。
2. 项目、类型、状态、搜索和来源 query 可组合筛选；汇总、空态和分页只基于当前结果。
3. 甲方变洽签、甲方报量复用既有量价/完成量实体；其余 6 类不出现无持久化实体支撑的明细网格。
4. 来源下钻、附件、草稿、已退回、进行中和终态均有真实可恢复旅程；未知参考动作不复制。
5. 390、768、1024、1280–1440px 无页面级横向溢出；长编号、完整金额、表格局部滚动、键盘焦点和首错定位通过运行态验收。
6. 验收/保修双视图的列表、详情、附件与表单均共用同一 acceptance ID；切换视图只改变投影，不创建平行记录。
7. 验收生命周期只能通过受控 command 单向推进，审计时间线只读已持久化事件；从全局列表、项目或合同往返时恢复视图、页签、锨点、滚动与行焦点。

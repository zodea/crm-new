# 基础信息 / 班组管理

> 路由：`/base/crew` · `/base/crew/form/:id?` · `/base/crew/:id`
> 页面：`pages/base/crew/index.vue` · `pages/base/crew/form/[[id]].vue` · `pages/base/crew/[id].vue`
> 表单蓝本：`crewForm`（ADR 0014）
> 状态：列表、整页表单、真实关系详情已实现 · 2026-07-30

## 定位

班组是跨项目共享的基础主数据。班组档案保存名称、工种能力、负责人、计薪默认值和责任指派粒度；项目参与、成员、工程量、工资与扣罚必须从现有业务事实读取，详情页不得建立第二份关系或展示静态成功数据。

本页遵守以下边界：

| 本页负责 | 本页不负责 |
|---|---|
| 新增、编辑班组档案 | 在详情页维护项目合同、工程量、工资或扣罚 |
| 展示班组能力和班组级计薪默认值 | 根据名称、备注或人员归属猜测项目关系 |
| 展示当前有效工人档案，并进入工人详情 | 将同班组全部工人推断为某项目成员 |
| 聚合已有项目、工程量、工资和扣罚事实 | 生成不存在的项目配置、单价或个人计薪覆盖 |
| 从真实项目与源单进入既有业务页面 | 在轻量弹窗内新增、编辑班组主数据 |

## 一、当前数据口径

现行表结构和软删除规则只以 [`DATABASE.md`](../DATABASE.md) 为准。班组界面读取以下真实关系：

| 界面内容 | 权威来源 | 关系口径 |
|---|---|---|
| 班组档案 | `crews` | 当前班组自身未删除 |
| 班组成员 | `workers.crew_id` | 只读有效工人；进入 `/base/worker/:id` |
| 成员当前项目 | `workers.current_project_id` | 项目祖先有效时显示并进入 `/project/:id` |
| 工程量责任 | `unit_assignments.crew_id` | 经 `units → floors → buildings → projects` 解析项目 |
| 阶段完成 | `unit_stage_completions.assignment_id` | 只汇总有效完成事实，保留责任审计语义 |
| 工资关联 | `wage_statements.crew_id` | 按有效工资单汇总项目、份数和金额 |
| 扣罚记录 | `penalty_records.crewId` | 只读有效项目处罚事实，并进入源记录 |
| 合作协议 | `file_refs(owner_type='crew')` | 由统一整页表单维护 |

项目关联是以下事实的去重并集：

1. 班组在场成员登记的当前项目；
2. 该班组有效工程量责任所属项目；
3. 该班组有效工资单所属项目。

同一项目可同时命中多种来源，详情以“在场成员 / 工程量责任 / 工资单”标签说明依据。任何来源为空时保持真实空态。

### 已废弃的幽灵关系

早期蓝本曾出现 `crew_workers`、`crew_project_config`、`crew_project_prices` 和 `crew_project_items`。这些表不在当前物理 schema 和迁移链中，不得在界面、查询或测试中引用，也不得用静态数组模拟。

因此本轮不提供以下写入能力：

- 班组 × 工人的计薪方式、比例和补贴覆盖；
- 班组 × 项目的分项单价；
- 从模板复制项目单价配置；
- 在班组详情中关联或移除工人。

如业务确认需要这些能力，应先建立 `needs-info` Issue，明确关系粒度、历史迁移和工资核算影响，再更新 `DATABASE.md` 和本页。

## 二、列表页 `/base/crew`

列表消费三类主数据共用的列表壳：

- 单行工具栏：名称/工种/负责人搜索、刷新、排序、工种筛选、状态筛选、新建；
- 紧凑数据表：班组名称、工种、负责人、脱敏电话、有效工人数、在场工人数、真实关联项目数、备注、档案状态和行操作；
- 班组名称及“详情”操作进入 `/base/crew/:id`；
- 编辑进入整页表单，删除使用软删除确认；
- 支持分页、加载失败、无数据和过滤无结果状态；
- 390 / 768 / 1024 / 1280–1440px 下，工具栏和密集表格只在自身区域横向滚动。

列表不展示无法从当前物理模型取得的“是否配置单价”。人员数和关联项目数复用本页第一节的真实关系口径，不能回引已废弃表名。

## 三、新增 / 编辑 `/base/crew/form/:id?`

班组使用统一整页表单壳，字段、校验与保存 action 仍由班组领域负责。

| 分区 | 字段 | 规则 |
|---|---|---|
| 基本信息 | 班组名称*、主工种*、负责人*、联系电话* | 非草稿均必填；有效班组名称不可重复 |
| 能力范围 | 可承接工种、可承接活项 | 主工种自动并入工种能力；保存 JSON 数组 |
| 计薪与提成 | 默认发放比例、房租补贴开关与单价、管理提成开关与单价 | 均为 `crews` 上的班组级默认值，不按项目复制 |
| 责任指派 | 班组 / 个人 | 保存 `assignment_level`，决定工程量责任是否允许下钻组内工人 |
| 合作协议 | 附件 | `file_refs(owner_type='crew')` |
| 备注 | 备注 | 班组档案说明，不参与关系推断 |

校验规则：

- 默认发放比例为 `0–1`；
- 补贴、提成单价不得为负数；
- 启用补贴或提成时必须设置对应单价；
- 保存和附件变更在同一领域事务中完成；
- 仍有有效 `workers.crew_id` 引用的班组不得删除；其他关联事实按通用软删除祖先可见性规则处理。

## 四、详情页 `/base/crew/:id`

详情页使用统一 `EntityDetailShell`，全宽纵向排列，不使用占位页或虚构页签。

### 4.1 摘要

摘要展示：

- 工种；
- 负责人；
- 脱敏联系电话；
- 有效工人数；
- 真实关联项目数。

长名称不得截断关键语义；窄窗不得造成整页横向滚动。编辑入口进入 `/base/crew/form/:id`。

### 4.2 工种与责任范围

展示 `crews` 上的真实字段：

- 可承接工种、可承接活项；
- 责任指派粒度；
- 默认发放比例；
- 房租补贴和管理提成开关及单价；
- 备注。

没有能力值时显示“尚未配置工种能力”或“未限制活项范围”，不补演示标签。

### 4.3 班组成员

成员表只读取 `workers.crew_id`，展示工人、工种、当前项目、在场状态、脱敏电话、参考日工资和进场日期。

- 工人姓名进入 `/base/worker/:id`；
- 真实 `linked_worker_id` 存在时，关联人员姓名同样进入工人详情；
- 当前项目存在时进入 `/project/:id`；
- 没有成员时显示“暂无班组成员”，并提示从工人档案建立归属。

### 4.4 项目参与与核算关联

项目表按第一节的三类真实来源聚合，展示：

- 项目名称、编号和来源标签；
- 在场成员数；
- 工程量责任户数 / 责任条数；
- 已完成阶段数；
- 工资单份数、工资单应付和已发金额。

项目名称进入 `/project/:id`。表格在移动端仅自身横向滚动；没有事实时显示“暂无项目关联”。

### 4.5 扣罚记录

扣罚区只读 `penalty_records.crewId`，展示日期、来源、项目、位置、原因、金额和状态。

- 项目进入 `/project/:id`；
- 记录进入 `/project/penalty/:id`；
- 没有有效事实时显示“暂无扣罚记录”；
- 本页不新增、编辑或审批扣罚。

## 五、隐私与可达性

- 列表和详情中的班组、成员电话统一使用中段脱敏，不把完整号码放入标题或辅助属性；
- 工人身份证、银行信息和证件正文不进入班组详情；
- 所有真实下钻入口使用可聚焦链接，保留可辨识名称；
- 横向滚动容器具有 `tabindex="0"` 和说明性 `aria-label`；
- 加载、错误、不存在和各关系空态使用共享状态面；
- 390 / 768 / 1024 / 1440px 验证长名称、摘要降列和三张密集表局部横滚。

## 六、验收要点

1. 列表、表单、详情均为生产路由，详情不是占位页。
2. 班组表单只写 `crews` 与 `file_refs(owner_type='crew')`。
3. 成员、项目、工资、工程量和扣罚均来自真实外键事实。
4. 工人、关联人员、项目和扣罚源记录均可下钻。
5. 电话脱敏，完整号码不进入详情 DOM。
6. 无成员、无项目和无扣罚分别显示明确空态。
7. 软删除记录及其被删除祖先不进入当前详情。
8. 不引用或模拟 `crew_workers`、`crew_project_config`、`crew_project_prices`、`crew_project_items`。

## 一、业务类型

新建第一步使用 `typeSelect` 选择：

1. 有合同-合同劳务
2. 有合同-材料
3. 有合同-专业分包
4. 有合同-机械
5. 有合同-其他
6. 无合同-零星采购
7. 预付款
8. 管理费
9. 项目费用
10. 公司付款

五类“有合同”显示合同情况和关联结算；预付款显示合同情况和预付款情况；公司付款不挂项目。“合同劳务”是劳务单位合同付款，和直接工人工资不是同一业务。类型一经产生真实分摊或支付记录，不允许直接改为不兼容类型，需撤销关联后再改。

“无合同-零星采购”不代表没有业务来源：零星材料必须先新增真实分供方，送货单或收据作为附件，按归属放入个人开支或具体项目并走费用报销流程；不得用付款申请直接替代报销，也不得把报销单或送货单直接当作银行支付事实。后续确实发生银行付款时，另按支付记录流程登记并人工确认。

## 二、表单分区

### 1. 基本信息

| 字段 | 控件/规则 |
|---|---|
| 付款申请编号 | 留空自动生成 |
| 付款申请名称 | 必填 |
| 业务类型 | 由新建第一步确定；设计稿中的只读业务类型镜像不重复保存 |
| 项目名称 | lookup；公司付款隐藏 |
| 收款单位 | lookup；按类型校验是否必填 |
| 关联合同 | 项目级联 lookup；五类有合同和预付款显示，公司付款可选择已有公司支出合同；保存领域、稳定 ID 和选择时版本 |
| 成本分类 | 合同劳务/专业分包/材料/机械/管理费/项目费用/其他；直接工人工资不在本表 |
| 申请金额 | 必填，正数 |
| 申请日期 | 必填 |
| 申请人 | 文本/人员选择 |
| 回票类型 | 先票后款/先款后票/无需发票 |
| 付款内容 | 多行文本 |
| 附件 | 最多 15 份 |

上述控件的实体字段、附件归属和存储例外直接见 [DATABASE](../DATABASE.md#entity-payment-application)，公共保存与回执见 [COMMANDS](../COMMANDS.md#command-envelope)；本页只维护交互和领域操作。

### 2. 合同情况（只读带出）

变更后合同金额、往期已结算、往期已付款和付款合同占比均从关联合同及其聚合查询实时计算，不作为用户可编辑字段。

### 3. 预付款情况

仅预付款类型显示“本次扣除预付款金额”和“扣除说明”；“是否预付款”由业务类型派生，不让用户重复填写。

### 4. 关联结算

五类有合同付款、“无合同-零星采购”和“项目费用”显示关联结算；公司付款可承接公司归属的原费用结算。新增行从当前项目或公司归属、实际收款身份以及合同范围一致的已确认结算中选择；无合同结算保留空合同，不创建虚拟合同。原费用、服务分供方、实际垫付方与付款额度的权威规则直接见 [DATABASE](../DATABASE.md#contract-freight-treatment)。

- 结算单号、名称与净额只读从真实结算来源带出；罚扣等有效调整沿原结算 owner 计算。归属或实际收款身份不匹配的源单不可选，来源不可用或净额未知时明确提示。
- 合同结算候选和保存均须核对可信合同领域、版本、项目和分供方；新结算的采用证据随申请版本冻结。旧结算仅有历史裸合同 ID 而缺明确映射时阻断；Q-SET-01 确认目前没有此类数据，暂不开发旧合同映射入口。
- 用户只编辑“本次关联金额”和备注；真实来源与分摊模型直接见 [DATABASE](../DATABASE.md#entity-payment-application)。
- 同一付款申请不得重复选择同一结算单。
- 草稿允许 `申请金额 − Σ关联结算金额 ≠ 0`，页面常驻显示差额。
- 提交前按当前类型核对分摊与申请金额；每个源单会再次核验稳定身份、当前版本和剩余额度。工人收款仅承接工人垫款清偿，工资实际支付仍进入既有工资流程。

历史清偿的原单缺失及旧未付承接按 2026-10-05 已确认的 [DATABASE 规则](../DATABASE.md#historical-expense-clearance)处理。界面分别显示原结算义务、当前核定结果、实际已付和可申请原因；旧结算未付部分须明确补核原结算申请关系，不能换成新费用或只按银行总额分摊。原费用核定、Other 明确关联、普通申请和真实银行实付已完成限定正式流程验证，具体原件、原号恢复、冷读及五档范围见该规则；缺证或来源变化继续显示不可用原因，不把历史批复 PAY-08 核验当作旧清偿关系已经确认。

### 5. 关联发票

`无需发票`隐藏并禁用本区，其他回票类型从真实发票台账选择：

- 发票号码、开票日期、含税金额只读从真实进项发票带出。
- 付款申请只可采用与自身归属一致的发票：项目付款须选择同一项目的项目票，公司付款须选择公司开销票；个人票和其他项目票不能因项目为空而混入公司或项目候选。既有错误关联不反写，新支付确认须先核对。
- 用户只编辑“本次关联金额”和备注；真实来源与分摊模型直接见 [DATABASE](../DATABASE.md#entity-payment-application)。
- `先票后款`：有合同的申请允许先保存和提交；实际支付确认前，已关联发票金额须等于申请金额且合同身份一致。无合同申请保留原有提交等额规则。
- `先款后票`：提交申请时允许 0 张发票；详情持续显示 `待回票金额 = max(申请金额 − Σ关联发票金额, 0)`。有合同且需要发票的申请，在实际支付确认前须先关联并核对发票，见[支付确认](#合同与发票核对)。
- `无需发票`：不得存在有效发票分摊；从其他类型切入前必须先撤销关联。
- 同一发票跨全部付款申请的有效关联金额合计不得超过含税金额；额度不足时拒绝保存并显示剩余可关联金额，并发提交也不能突破该上限。

### 6. 审批与支付

本期批复金额和审批备注按已确认方案持久化；[ADR 0015 决策 6](../../adr/0015-form-persistence-and-payment-reconciliation.md)保留决策依据。已付金额、实际支付金额和支付状态均为只读派生值；现行关系、公式、存量字段兼容和确认约束统一见 [`DATABASE 支付事实`](../DATABASE.md#entity-payment-record)。本页负责显示支付记录、分摊明细、未付提示和源单下钻。

[#439](https://github.com/zodea/crm-new/issues/439) 已接本期批复的输入语义：新建留空、填写零元和清空后保存均按真实输入往返；表单明确提示空与零的区别，临时非法输入保留可编辑状态并由保存域拒绝。详情与付款管理用“未填写”或“历史批复待核验”解释空金额，已确认实付照常显示。历史待核验记录的完整批复/余额合计显示不完整，不能冒充零元或已付清。历史来源、金额及实际核验范围直接见 [DATABASE 的 PAY-08](../DATABASE.md#entity-payment-record)。

历史批复待核验的申请在原整页编辑入口显示“历史付款业务核验”。先保存申请编辑和实际依据原件，再填写“核实累计应付金额”“核实累计可付金额”及业务依据，选取已保存原件，执行“保存业务核验”；页面显示当前核验原因，成功后显示冻结结论、核验人和时间。未保存的普通输入或附件先保留并完成原保存；核验不混入整单改写。提交未知、保存后读失败及版本变化按 [COMMANDS](../COMMANDS.md#f3-finance-payment-verification)恢复，成功回执不代替同一目标的可靠后读。实际来源不可用时依页面原因核对，原回单仍可在支付记录保存草稿。

## 三、保存与提交

### 保存草稿

- 允许业务必填字段暂空、结算/发票金额不平。
- 页面必须显示结算差额、发票差额或待回票金额，不能以保存成功掩盖未勾稽。
- 草稿保存的事务、失败和回执行为直接沿 [COMMANDS](../COMMANDS.md#command-envelope)，本页仅规定允许暂存的业务状态及显示。

### 保存并提交

除字段必填外，按顺序校验：

1. 类型、项目/合同/收款单位组合合法。
2. 按业务类型与实际收款身份核对所需结算分摊、原费用采用和剩余额度。
3. 回票类型规则成立。
4. 每张发票跨申请累计关联不超含税金额。
5. `无需发票`不存在有效发票分摊。

失败时定位到对应分区和行，不部分提交。

## 六、支付记录与 OCR

### 合同与发票核对

Q-INV-09 / Q-INV-11：付款申请有合同且回票类型需要发票时，保存和提交申请仍按上文规则；实际支付确认前必须先在申请中指定发票，并以合同领域和稳定 ID 核对每张关联发票与申请合同一致。不按名称、编号或同一个 ID 跨领域猜测，权限不足、来源不完整或合同身份歧义时明确阻断并保留支付草稿。预付款与“先款后票”不因名称自动豁免；没有合同或明确无需发票的申请保持既有规则。一次支付涉及多个申请时逐项核对，采用当时的申请版本和发票证据与原确认回执一同冻结；后续合同或发票变化不改写已确认历史，原编号重放仍返回原回执。旧库迁入按原始历史保全，不追溯制造新确认。

本业务门槛来自用户确认，不作为所有交易的法定付款前置条件。有关发票取得、真实业务和票面内容，参见国家税务总局现行[《中华人民共和国发票管理办法》](https://fgk.chinatax.gov.cn/zcfgk/c100010/c5195084/content.html)及[实施细则](https://fgk.chinatax.gov.cn/zcfgk/c100011/c5221006/content.html)；具体交易仍依其事实和适用规定核对。

页面提供图片/PDF识别和手工录入两种入口，并排展示原图、识别值、置信度和人工修订值；OCR 失败时允许切换手工录入。支付事实、人工确认、重复提示、分摊守恒和撤回后的计算直接见 [DATABASE 支付事实](../DATABASE.md#entity-payment-record)；[ADR 0015 决策 5-6](../../adr/0015-form-persistence-and-payment-reconciliation.md)保留历史依据。样本数值场景见[睿璟验收清单](../../migration/ruijing-acceptance.md)。

## 七、验收要点

- 所有 lookup 保存真实 ID，结算/发票源字段不可手填。
- 草稿不平可保存且差额可见；提交态按类型严格勾稽。
- `先款后票`可无票提交申请并能后补；有合同且需票的实际支付须先核对同一合同的发票，待回票金额实时减少。
- `无需发票`无法误挂发票。
- 同一发票跨付款申请不会超额关联，并发保存也受事务保护。
- 付款申请已付金额只能由已确认支付记录分摊产生。
- 1:1、1:N 和 N:1 支付分摊均能保存、撤回和重算。
- OCR 或手录但未人工确认的支付记录不进入任何经营汇总。
- 直接工人工资不混入“有合同-合同劳务”。
- 刷新后所有用户可编辑字段、分摊行和附件引用均恢复；只读聚合不落副本。

### 1. 付款申请列表

参考专属列覆盖申请编号/名称、项目、收款单位、申请/批复/实际支付金额、成本预算、业务类型、成本分类组成、支付/审批状态、合同、申请日期/申请人、累计关联结算、生效/回票状态、当前审批人、支付凭证和修改人。当前参考样本为明确的 `共0条`，只能确认字段与空态，不能外推未知详情或审批接口。

本地列表读模型应在现有 `payment_applications` 上组合真实聚合：

- `paidAmount` 只取已确认 `payment_record_application_allocations`；
- `settlementAllocatedAmount` 只取有效结算分摊；
- `invoiceAllocatedAmount/pendingInvoiceAmount` 只取有效发票分摊；
- `project/supplier/contract` 使用 [READ-MODELS.md](../READ-MODELS.md) 的来源感知实体引用，目标注册成功后才成为详情链接；

### 2. 付款管理

当前正式工作台复用本域实际中央清单与付款详情，不另存一套付款事实；同次读取核对真实身份、权限与来源版本。来源变化撤下旧正式数据；测试来源只读。已付来自已确认的原支付分摊，工人垫付清偿使用冻结工人稳定身份，工资分区沿 P4 独立来源。

参考工作台按待支付、已支付、无需支付和全部分段，列为申请编号、项目、收款单位、合同、付款内容、申请日期/金额、剩余待支付、来源单据/业务类型、所属部门和支付状态。2026-08-13 已观察到本地独立工作台和小规模演示样本；[#413](https://github.com/zodea/crm-new/issues/413) 按当前提交核实专属列、真实分摊、各来源详情与回读，不能把当时的样本或缺口当本轮状态。

`sourceDocument` 遵循现行 `EntityRefDTO` / `NavigationIntentDTO` 与 Target Registry 契约；缺稳定 ID、来源不一致或目标未注册时显示具体不可达原因，不由 DTO 拼可选路由，也不按单号/名称猜路由。

工资实际收付在付款管理中作为独立只读分区，来源为工资 Repository 的项目台账。该分区按稳定原工资/收付身份下钻，保留返回入口；金额不并入 `payment_applications`、`payment_records` 或往来指标。规则见[工资页面第六节](./subcontract-payroll.md#六独立更正与实际收付p4)，操作说明见[工资更正指南](../../guides/payroll-adjustments.md)。

### 3. 当前不扩张的相邻页面

参考站另有保证金申请/退还和备用金申请/退还；本轮只确认其专属列、支付/退还状态与真实空态。本地当前没有对应生产路由或持久化实体，故不并入付款申请表、不补 Mock，也不在本工作单元新增模块。后续只有在本地范围明确扩展时，才按独立申请头、退还事实和支付分摊设计，不能复用付款申请自由文本冒充。

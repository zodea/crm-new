# 付款申请 — 10 类业务表单 + 结算/发票勾稽

> 路由：`/finance/payment` · `/finance/payment/new` · `/finance/payment/:id`（编辑）· `/finance/payment/:id/detail`（只读详情）
> 设计来源：`DC重构设计源码/kit/PayApplyScreen.jsx` · `kit/forms/FinanceForms.jsx` 的 `payApplyForm`
> 表单形态：[ADR 0014](../../adr/0014-full-page-entity-forms.md) 整页实体表单
> 持久化与勾稽：[ADR 0015](../../adr/0015-form-persistence-and-payment-reconciliation.md)
> 数据模型：[DATABASE.md §2.4 / §3.3 / §4.2.1](../DATABASE.md)

付款申请是支出侧起点。页面按业务类型显隐字段，但所有类型共享同一表单流程；关联结算和关联发票必须选择真实源单，不接受自由文本假关联。

---

## 一、业务类型

新建第一步使用 `typeSelect` 选择：

1. 有合同-合同劳务
2. 有合同-材料
3. 有合同-专业分包
4. 有合同-机械
5. 有合同-其他
6. 无合同-零星采购
7. 预付款
8. 管理费
9. 项目费用
10. 公司付款

五类“有合同”显示合同情况和关联结算；预付款显示合同情况和预付款情况；公司付款不挂项目。“合同劳务”是劳务单位合同付款，和直接工人工资不是同一业务。类型一经产生真实分摊或支付记录，不允许直接改为不兼容类型，需撤销关联后再改。

“无合同-零星采购”不代表没有业务来源：零星材料必须先新增真实分供方，送货单或收据作为附件，按归属放入个人开支或具体项目并走费用报销流程；不得用付款申请直接替代报销，也不得把报销单或送货单直接当作银行支付事实。后续确实发生银行付款时，另按支付记录流程登记并人工确认。

## 二、表单分区

### 1. 基本信息

| 字段 | 控件/规则 |
|---|---|
| 付款申请编号 | 留空自动生成 |
| 付款申请名称 | 必填 |
| 业务类型 | 由新建第一步确定；设计稿中的只读业务类型镜像不重复保存 |
| 项目名称 | lookup；公司付款隐藏 |
| 收款单位 | lookup；按类型校验是否必填 |
| 关联合同 | 项目级联 lookup；五类有合同/预付款显示 |
| 成本分类 | 合同劳务/专业分包/材料/机械/管理费/项目费用/其他；直接工人工资不在本表 |
| 申请金额 | 必填，正数 |
| 申请日期 | 必填 |
| 申请人 | 文本/人员选择 |
| 回票类型 | 先票后款/先款后票/无需发票 |
| 付款内容 | 多行文本 |
| 附件 | 最多 15 份 |

上述控件如何持久化、附件归属和字段例外统一见 ADR 0015 与 `DATABASE.md`，本页只维护交互和校验。

### 2. 合同情况（只读带出）

变更后合同金额、往期已结算、往期已付款和付款合同占比均从关联合同及其聚合查询实时计算，不作为用户可编辑字段。

### 3. 预付款情况

仅预付款类型显示“本次扣除预付款金额”和“扣除说明”；“是否预付款”由业务类型派生，不让用户重复填写。

### 4. 关联结算

仅五类有合同付款显示。新增行必须从当前项目/合同的真实结算单中选择：

- 结算单号、结算名称、含税结算金额只读从真实支出结算源单带出；项目/合同不匹配的源单不可选。
- 用户只编辑“本次关联金额”和备注；真实来源与分摊模型见 ADR 0015 和 `DATABASE.md`。
- 同一付款申请不得重复选择同一结算单。
- 草稿允许 `申请金额 − Σ关联结算金额 ≠ 0`，页面常驻显示差额。
- 保存并提交时必须 `Σ关联结算金额 = 申请金额`；无关联结算区的类型不执行此规则。

### 5. 关联发票

`无需发票`隐藏并禁用本区，其他回票类型从真实发票台账选择：

- 发票号码、开票日期、含税金额只读从真实进项发票带出。
- 用户只编辑“本次关联金额”和备注；真实来源与分摊模型见 ADR 0015 和 `DATABASE.md`。
- `先票后款`：提交时 `Σ本次关联发票金额 = 申请金额`。
- `先款后票`：提交时允许 0 张发票；详情持续显示 `待回票金额 = max(申请金额 − Σ关联发票金额, 0)`，后续补关联。
- `无需发票`：不得存在有效发票分摊；从其他类型切入前必须先撤销关联。
- 同一发票跨全部付款申请的有效关联金额合计不得超过含税金额；额度不足时拒绝保存并显示剩余可关联金额，并发提交也不能突破该上限。

### 6. 审批与支付

本期批复金额和审批备注按 ADR 0015 持久化。已付金额、实际支付金额和支付状态均为只读派生值；关系、公式、存量字段兼容和确认约束只在 [ADR 0015 决策 6](../../adr/0015-form-persistence-and-payment-reconciliation.md) 与 [`DATABASE.md §10.2`](../DATABASE.md) 维护。本页负责显示支付记录、分摊明细、未付提示和源单下钻。

[#439](https://github.com/zodea/crm-new/issues/439) 已接本期批复的输入语义：新建留空、填写零元和清空后保存均按真实输入往返；表单明确提示空与零的区别，临时非法输入保留可编辑状态并由保存域拒绝。详情与付款管理用“未填写”或“历史批复待核验”解释空金额，已确认实付照常显示。历史待核验记录的完整批复/余额合计显示不完整，不能冒充零元或已付清。仅改备注或放弃修改不会确认历史来源；历史新支付确认政策仍见 DATABASE 链接的 PAY-08 待裁定项。

## 三、保存与提交

### 保存草稿

- 允许业务必填字段暂空、结算/发票金额不平。
- 页面必须显示结算差额、发票差额或待回票金额，不能以保存成功掩盖未勾稽。
- 保存必须是原子操作：任一分区失败时不显示成功，也不留下部分更新；事务写入拓扑只在 ADR 0015 与 `DATABASE.md` 维护。

### 保存并提交

除字段必填外，按顺序校验：

1. 类型、项目/合同/收款单位组合合法。
2. 五类有合同的结算分摊合计等于申请金额。
3. 回票类型规则成立。
4. 每张发票跨申请累计关联不超含税金额。
5. `无需发票`不存在有效发票分摊。

失败时定位到对应分区和行，不部分提交。

## 四、列表与详情

- 默认视图可继续按待追回发票筛选，但显示值必须由回票类型与待回票金额派生。
- 列表至少展示编号、名称、类型、项目/收款单位、申请/批复/已付金额、回票状态、支付状态、申请日期。
- 点击列表名称进入只读详情；编辑动作仍进入 `/finance/payment/:id` 整页表单。详情分别显示合同聚合、结算分摊、发票分摊与支付记录分摊；每笔支付显示回单、金额、日期、人工确认状态和本申请分摊金额。源单号使用 EntityLink，下钻到真实源单。
- 详情页的智能业务洞察只读取真实源单实时派生审批状态、结算/发票勾稽、付款上限和跨项目/分供方摘要；没有审批数据时不补造审批人、时间线或评论。
- 金额穿透遵守全站 MoneyLink 契约，0/空退化为普通文本。

## 七、验收要点

- 所有 lookup 保存真实 ID，结算/发票源字段不可手填。
- 草稿不平可保存且差额可见；提交态按类型严格勾稽。
- `先款后票`可无票提交并能后补，待回票金额实时减少。
- `无需发票`无法误挂发票。
- 同一发票跨付款申请不会超额关联，并发保存也受事务保护。
- 付款申请已付金额只能由已确认支付记录分摊产生。
- 1:1、1:N 和 N:1 支付分摊均能保存、撤回和重算。
- OCR 或手录但未人工确认的支付记录不进入任何经营汇总。
- 直接工人工资不混入“有合同-合同劳务”。
- 刷新后所有用户可编辑字段、分摊行和附件引用均恢复；只读聚合不落副本。

## 八、运行态列表、付款管理与关联跳转（2026-08-13）

直接证据见 `runtime-reference-audit.md` 的 `R-FINANCE-FLOW-LIVE`。

### 1. 付款申请列表

参考专属列覆盖申请编号/名称、项目、收款单位、申请/批复/实际支付金额、成本预算、业务类型、成本分类组成、支付/审批状态、合同、申请日期/申请人、累计关联结算、生效/回票状态、当前审批人、支付凭证和修改人。当前参考样本为明确的 `共0条`，只能确认字段与空态，不能外推未知详情或审批接口。

本地列表读模型应在现有 `payment_applications` 上组合真实聚合：

- `paidAmount` 只取已确认 `payment_record_application_allocations`；
- `settlementAllocatedAmount` 只取有效结算分摊；
- `invoiceAllocatedAmount/pendingInvoiceAmount` 只取有效发票分摊；
- `project/supplier/contract` 使用 [READ-MODELS.md](../READ-MODELS.md) 的来源感知实体引用，目标注册成功后才成为详情链接；
- 名称主链接进入 `/finance/payment/:id/detail`，编辑保持独立动作，来源 query、筛选、页码和滚动位置可恢复。

### 2. 付款管理

参考工作台按待支付、已支付、无需支付和全部分段，列为申请编号、项目、收款单位、合同、付款内容、申请日期/金额、剩余待支付、来源单据/业务类型、所属部门和支付状态。2026-08-13 已观察到本地独立工作台和小规模演示样本；[#413](https://github.com/zodea/crm-new/issues/413) 按当前提交核实专属列、真实分摊、各来源详情与回读，不能把当时的样本或缺口当本轮状态。

`sourceDocument` 遵循现行 `EntityRefDTO` / `NavigationIntentDTO` 与 Target Registry 契约；缺稳定 ID、来源不一致或目标未注册时显示具体不可达原因，不由 DTO 拼可选路由，也不按单号/名称猜路由。

工资实际收付在付款管理中作为独立只读分区，来源为工资 Repository 的项目台账。该分区按稳定原工资/收付身份下钻，保留返回入口；金额不并入 `payment_applications`、`payment_records` 或往来指标。P4 的跨域限定状态见[工资实施票](../../research/issue-review-2026-09-11/payroll-tickets/04-central-adjustments-and-actual-payments.md)，操作说明见[工资更正指南](../../guides/payroll-adjustments.md)。

### 3. 当前不扩张的相邻页面

参考站另有保证金申请/退还和备用金申请/退还；本轮只确认其专属列、支付/退还状态与真实空态。本地当前没有对应生产路由或持久化实体，故不并入付款申请表、不补 Mock，也不在本工作单元新增模块。后续只有在本地范围明确扩展时，才按独立申请头、退还事实和支付分摊设计，不能复用付款申请自由文本冒充。

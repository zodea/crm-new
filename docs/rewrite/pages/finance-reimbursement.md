# 费用报销 — 报销头 + 费用明细

> 表单蓝本：`reimburseForm`
> 持久化权威：`DATABASE.md` 的 `expense_reimbursements` / `expense_reimbursement_lines`

## 新增/编辑

| 分区 | 字段与规则 |
|---|---|
| 基本信息 | 报销单号、报销／垫付工人或分供方*、采用时姓名快照及历史原文、新建工程名称*（动态搜索真实工程及施工主合同）、费用类别、报销日期*；旧无项目及冻结记录保留 |
| 报销明细 | 费用项目*、发生日期、金额*、实际服务分供方、新原费用每行对应一份施工主合同、明示原费用引用、备注；支持增删复制与汇总 |
| 审批与备注 | 报销总额（按明细汇总）、状态、发票张数、报销事由、票据附件 |

报销总额由有效明细金额汇总，页面不维护可与明细永久分叉的第二份金额。新建工程动态搜索真实项目及施工主合同，同工程多合同按名称和编号区分；新建费用与逐行工程归属在同一个原提交内保存，草稿也须选择。共用费用先拆真实明细，同工程不同主合同可逐行明选，跨工程分单。公司合同头保独立，新公司业务费用仍按实际工程明细记录；历史无项目记录保留，不建立虚拟项目。现行创建与关联规则见[合同及原费用指南](../../guides/core-contract-and-boq.md#按施工主合同核对材料与实际费用)。

## 无合同零星材料

无合同的零星材料仍先新增真实分供方，再将送货单或收据作为票据附件放入实际工程的业务费用，继续走本报销流程。纯个人消费不新建业务记录；个人垫付的项目业务费用保留真实垫付身份。没有材料采购合同不等于可以省略分供方，也不等于报销单已经形成银行支付事实；实际付款仍需另建支付记录并完成人工核对。

## 生命周期与成本

`草稿 → 审批中 → 已审批 → 已付款` 为界面状态；数据库使用稳定状态码映射。成本资格、原费用身份和清偿防重复只按 [DATABASE 的费用报销与明细](../DATABASE.md#费用报销与明细)。实际资金流出仍以已确认支付事实为准。

当前表单从同一中央工作区的全局工人或现有分供方清单明选报销／垫付身份，实际服务交易方在费用行独立选择；采用时名称冻结，旧申请人文本保留。人员、实际交易方与工资付款归属按 [DATABASE 的已确认收付身份](../DATABASE.md#actual-counterparty-identities)，费用关系按[费用报销与明细](../DATABASE.md#费用报销与明细)，不按姓名猜接。编辑、重排和读取保留原费用行 ID 与创建证据，复制和新增使用新 ID。

清偿时从同归属原费用清单选择已记录费用。具备稳定垫付身份的来源通过本次同一身份、原费用和金额核验后可提交；历史缺身份的来源保留待核实草稿。清偿不再次计入成本，报销提交或确认不会产生银行支付记录。无合同费用核验后的结算沿原其他支出结算 owner 采用原明细，再进入付款申请及支付记录；服务分供方与实际收款方分别冻结。已有旧清偿的原费用按 2026-10-05 已确认的[历史承接规则](../DATABASE.md#historical-expense-clearance)核定关系及份额，不能凭清偿金额直接认定银行已支付。

本轮原费用整页已接“旧清偿替代核验”：原费用、逐项旧记录或明确补证、正金额及匹配依据、已保存替代文件、核验说明分别填写；新可采用额与旧已付／未付分开显示。已确认原费用的替代文件只通过“保存新增替代原件”追加，不能改原头、行或删除原文件。核定与普通输入分开提交，撤权撤下旧证明，后来输入及未知原号恢复沿 [COMMANDS](../COMMANDS.md#historical-expense-clearance-command)；原纸缺失场景的真实替代文件、核定及冷读取已通过正式整页和五档界面验收，精确外部电子原单缺失声明的验证层次见 [DATABASE](../DATABASE.md#historical-expense-clearance)。

原件保存真实字节及摘要；旧完整 Native 来源确实仅有元数据的附件按精确缺件证据保留，显示正文未知。中央采用、草稿、提交、编辑和恢复沿现有持久命令与版本；已保存而回读失败时保留原回执并只重试读取，后来修改和附件继续留在输入稿。结果未知时核对原编号，登录或来源切换即时撤下旧读取事实并保留输入。公共原命令与读回要求直接按 [COMMANDS](../COMMANDS.md)。

## 验收

1. 明细刷新后不丢失，总额始终等于有效明细合计。
2. 票据附件通过 `file_refs` 保存。
3. 新草稿必须选择真实工程／施工主合同，其余可不完整；新提交时至少明确选择工人或分供方、日期和一条正金额明细。原命令回执与费用及逐行归属均须可靠读回，历史原文不做同名映射。

2026-08-13 参考与本地走查均为空；[#413](https://github.com/zodea/crm-new/issues/413) 按当前数据源重新核实列表，不用演示行补空态。列表读模型至少返回 `id/no/project/company/bizType/category/applicant/applicationDate/reason/reimbursedAmount/advanceOffset/deductionAmount/payableAmount/approvalStatus/paidAmount/unpaidAmount/paymentStatus/effectiveStatus/costCategory`，其中：

- `paidAmount/unpaidAmount` 只从已确认支付及分摊派生；
- 备用金域沿用本轮排除；其抵扣列明确不适用，不展示为待接后台任务，也不伪造 `0`；后续若明确扩域才调整数据契约；
- 历史公司报销的 `project` 可空，不创建虚拟项目；新业务费用按上述现行工程选择规则，不将历史空值当作新建默认。

申请编号主链接应进入只读详情，编辑保持独立动作；列表无数据时仍保留分类、表头、筛选和分页。
